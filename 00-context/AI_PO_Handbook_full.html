第一章 · Git 工作流:团队协作的操作系统

本章目标:让你能在本周内跟团队定下一套 Git 规范,让 AI 生成的代码有 review,让每个 commit 可追溯。

1.1 痛点切入 · 这一幕你熟不熟?

你在 R·Agent 项目里跑通了 anchor verification 逻辑。开心地 push 了。

三天后,后端同事说:“我昨天改了 normalize 模块,现在 anchor 校验挂了。”

你打开 git log,看到一串这样的 commit:

* a3f2c1 update
* 7b9e0d fix
* 2d4a88 WIP
* 9f1e2c save
* 88cc11 works now

你无法回答以下任何一个问题:

  • 是谁改的?(能看到作者,但不知道改了什么)
  • 改了什么?(必须打开 diff 一行行看)
  • 为什么改?(没人写原因)
  • 能回滚吗?(可以,但回滚哪个?)
  • 测过吗?(不知道,没有 CI)
  • 跟哪个需求有关?(commit 消息里没提)

这不是”写 commit 消息不认真”的问题。这是团队没有一套协作协议的问题。

每一个 commit,本质上是一次”对代码仓库状态的变更申请”。没有协议,就像两个人用不同的语言谈合同 —— 都以为自己说清楚了,其实谁也没看懂。

这一章要解决的核心问题是:让你的 Git repo 变成一份可审计、可回溯、AI 改代码也能被管住的工程文档。

1.2 费曼式核心 · Git 工作流的底层 3 个原理

这是本章最重要的一节。如果你只记三件事,就记这三个。

原理一:Git 的本质是带版本的有向无环图

忘掉教程里的”分支”“合并”这些视觉化隐喻。底层看,git 是:

  • 一棵 commit 树(准确说是 DAG,有向无环图)
  • 每个 commit 节点指向它的父 commit(可能一个父,也可能多个父)
  • 分支只是一个”指向某个 commit 节点的指针”,仅此而已
  • main 这个词不特殊,它只是一个约定俗成名字的指针

💡 术语小词典 - DAG(Directed Acyclic Graph,有向无环图):一种数据结构。“有向”= 连线带箭头方向;“无环”= 没有任何一条路径能从某点出发转一圈回到自己。git 的 commit 历史就是这种结构 —— 每个 commit 指向它的前一个 commit(父),永远不会指回自己。 - commit 节点:每次你 git commit,git 就生成一个”节点”对象,存着这次的变更 + 作者 + 时间 + 一个父节点的引用。DAG 里的每个圆圈就是一个节点。 - 父 commit:节点指向的”前一个节点”。merge 产生的节点有两个父(因为合并了两条线);普通 commit 只有一个父。 - 指针:git 里一个分支名(比如 main)本质上就是一个文件,存着一个 commit 的哈希值。“切换分支”其实就是”把 HEAD 这个指针换成指向另一个 commit”。没有复制文件,没有魔法,就是指针移动。

所以: - 创建分支 = 新建一个指针 - merge = 创建一个有两个父 commit 的新节点 - rebase = 把一串 commit 节点复制到另一个位置,旧节点变成孤儿 - squash = 把多个 commit 合成一个新 commit

💡 术语小词典 · 三种操作的差别先点一下(1.4 / 1.5 会详细展开) - merge:把两条分支的历史”缝合”,生成一个有两个父的新节点。历史完整保留,但多了合并提交,历史图形看起来有”分叉+合并”的菱形。 - rebase:把你这条分支上的 commit 逐个复制到目标分支的最新位置。旧节点变成”孤儿”(没有指针指向,会被 git 回收)。历史变成一条直线,看起来干净。 - squash:把多个 commit 压缩成一个。通常在合并 PR 时用,把 feature 分支上的 10 个 WIP 压成一个”feat(xxx): …“提交。

看懂这张图,你就看懂了 git 90% 的概念。分支?只是绿色节点和蓝色节点的不同指针。

原理二:操作可以本地回滚,协作不可以

这条是所有 git 新手踩坑的根源。

  • 本地未 push 的 commit:你爱怎么玩怎么玩,rebase、amend、reset 都随便
  • 已 push 到远程的 commit:尤其是别人基于它工作的,动它就是犯罪

💡 三个常见的”改历史”操作(现在只需要知道名字,不用会) - git commit --amend:修改上一个 commit(改消息或补充文件)。本质是用新 commit 替换旧 commit,所以也改写了历史。 - git reset:把分支指针往前挪几格,“抹掉”若干个 commit。有三种模式(soft / mixed / hard),安全性和破坏力不同。 - HEAD:一个特殊指针,永远指向”你当前所在的 commit”。HEAD~1 就是”上一个 commit”,HEAD~4 就是”往回四格”。上文 git rebase -i HEAD~4 就是”从现在起往回四个 commit,进交互式 rebase”。

为什么?因为你改了 commit 历史,别人的本地仓库还停留在旧历史上。他下次 pull 会拉到一堆诡异的冲突,而且很难恢复。

这条原理推导出一条铁律: > 不要 force push 到共享分支(main、develop、别人在用的 feature 分支)。 > force push 到自己的私有分支可以,前提是你独占这个分支。

💡 术语小词典 - 共享分支 vs 私有分支:不是 git 层面的区分,是团队约定层面的区分。“共享”= 多个人会从它拉代码 / 基于它干活(比如 main、develop);“私有”= 只有你自己在用(比如你的 feature/anchor-verify)。判断方法:有没有别人 pull 过这个分支? 有,就是共享。 - push:把本地 commit 上传到远程仓库(GitHub / GitLab)。普通 push 只能”追加”,不能”改写”。 - force push(git push --force):强制上传,允许覆盖远程已有的 commit 历史。相当于对远程说”听我的,你之前的历史作废”。对共享分支用,会让队友的本地仓库错乱。 - --force-with-lease:force push 的安全版本。会先检查”远程分支现在是不是我上次看到的样子”,如果有别人偷偷推了东西进去就拒绝覆盖。本章 1.4 动作 6 会演示用法。永远优先用它,不用 --force。

原理三:commit 是给未来的你和团队看的,不是给 git 看的

这条听起来像鸡汤,但它决定了整套规范的意义。

假设 6 个月后,R·Agent 在生产环境出了个诡异的 bug,你怀疑是某次对 normalize 模块的改动引入的。你会怎么做?

git log --oneline src/normalize.py

如果 log 长这样:

7b9e0d fix
a3f2c1 update  
2d4a88 WIP

你完了。你要一个 commit 一个 commit 打开 diff 看,凭记忆推理当时为什么改。

如果 log 长这样:

feat(normalize): 支持连续换行符的归一化,修复 anchor 误判 #142
fix(normalize): 处理 \r\n 和 \n 混用时的边界问题
refactor(normalize): 提取字符计数为独立函数,便于单测

你三分钟就能定位。feat(normalize): 支持连续换行符 —— 就是它,打开一看就懂了。

这就是为什么要学 Conventional Commits。不是为了好看,是为了6 个月后的自己。

1.3 要学什么 · 知识点清单

学完这章,你需要掌握以下概念:

分支策略三选一(只需了解三种,选一种用)

  • Git Flow:5 种分支(main / develop / feature / release / hotfix),适合有调度发布的大团队
  • GitHub Flow:main + 短 feature 分支,所有改动走 PR,适合持续部署
  • Trunk-Based Development:几乎所有人直接在 main 上工作,靠 feature flag 隔离未完成功能,需要极强自动化

Conventional Commits 规范

  • <type>(<scope>): <description> 的结构
  • 7 个常用 type:feat, fix, refactor, docs, test, chore, perf
  • BREAKING CHANGE: footer 和 ! 标记
  • Scope 的用法(feat(normalize))

SemVer 与 commits 的映射

  • fix: → PATCH bump (1.2.3 → 1.2.4)
  • feat: → MINOR bump (1.2.3 → 1.3.0)
  • BREAKING CHANGE: → MAJOR bump (1.2.3 → 2.0.0)

Merge vs Rebase vs Squash

  • 各自的历史图形是什么样
  • 什么时候用哪个
  • 一条铁律:私有分支用 rebase,共享分支用 merge

PR 协作机制

  • Branch protection rule
  • Required status checks
  • Required reviewers
  • PR template

本地 hooks

  • pre-commit hook 是什么
  • commitlint / husky 的作用
  • 为什么”不靠人自觉,靠工具强制”

工作区三态模型(理解后所有 git 命令都变清晰)

  • Working Directory(工作区):你正在编辑的文件
  • Staging Area / Index(暂存区):git add 之后、git commit 之前的区域
  • Repository(仓库):git commit 之后进入的历史记录

远程跟踪与同步

  • origin:远程仓库的别名(通常指向 GitHub)
  • origin/main:本地记录的”远程 main 的最后一次已知状态”
  • fetch vs pull 的差别(核心差别会改你”本地”还是”本地的远程副本”)

冲突(Merge Conflict)

  • 什么时候会发生(两个分支改了同一个文件的同一行)
  • git 留下的标记(<<<<<<< / ======= / >>>>>>>)
  • 解决后的流程(手动改 → add → continue)

附:分支命名规范(定下来,全团队统一)

分支名就是一种低成本的元数据 —— 同事看一眼就知道你在干嘛。推荐格式:

<type>/<短描述-用短横线>
前缀 用途 例子
feature/ 新功能 feature/anchor-verify
fix/ 修 bug fix/crlf-handling
refactor/ 重构 refactor/pipeline-stages
docs/ 文档 docs/api-contract

几条铁律: - 全小写,用短横线不用下划线(fix/handle-crlf 而不是 fix_handle_CRLF) - 短描述 ≤ 40 字符,讲清楚”做什么”即可 - 带了 issue/ticket 号更好:feature/142-anchor-verify - 不要用个人名前缀(jianan/xxx)—— 分支是项目资产,不是个人领地

动作 2:写你的第一个 Conventional Commit

R·Agent 的例子:

# ❌ 旧习惯
git commit -m "update normalize"

# ✅ 新习惯
git commit -m "feat(normalize): 添加 \r\n 到 \n 的归一化

为了支持从 Windows 导出的 docx,需要在 normalize 阶段
统一换行符。加入测试用例验证归一化后的 anchor 位置
仍然正确。

Refs: #142"

三件事: - 标题第一行:<type>(<scope>): <description>,英文冒号,空格,小写动词开头,不加句号 - 标题 < 72 字符 - 正文写”为什么”,不写”做了什么”(代码会告诉你做了什么)

动作 3:配 commitlint 强制格式

这一步是关键:如果不强制,没人会遵守。

💡 术语小词典 - hook(钩子):git 的一个机制 —— 在”commit 前”“push 前”等关键时刻自动执行一段脚本。比如 pre-commit 在你 commit 之前跑,可以做格式检查;commit-msg 在你写完 commit 消息之后跑,可以校验消息格式。git 原生支持,但原生配置麻烦。 - husky:一个 npm 工具,帮你更方便地管理 git hooks。它把 hook 脚本放在项目的 .husky/ 目录,这样克隆项目的人自动就有同样的 hooks,不需要手动配。 - commitlint:一个校验工具,检查 commit 消息符不符合 Conventional Commits 规范。通常和 husky 搭配用:husky 负责”在 commit-msg 这个 hook 点触发”,commitlint 负责”检查内容对不对”。

# 安装
npm install -D @commitlint/cli @commitlint/config-conventional husky

# 配置
echo "module.exports = {extends: ['@commitlint/config-conventional']}" \
  > commitlint.config.js

# 启用 husky
npx husky init
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg
chmod +x .husky/commit-msg

配完之后,任何不符合格式的 commit 都会被拒:

$ git commit -m "update stuff"
✖ subject may not be empty
✖ type may not be empty

规范从文档变成了强制。这是本章最重要的一句话,贯穿整本书。

动作 5:配 branch protection

动作 6:学会 rebase 一次

在你自己的 feature 分支上:

# 场景:你的 feature 分支落后 main 几个 commit,要同步
git checkout feature/anchor-verify
git fetch origin
git rebase origin/main

# 如果有冲突,解决后:
git add <resolved-files>
git rebase --continue

# 推到自己的分支(因为改写了历史,需要 force push)
git push --force-with-lease origin feature/anchor-verify

关键点:用 --force-with-lease 而不是 --force。前者会检查远程分支是不是你期望的版本,防止你覆盖队友的工作。

动作 7:用 interactive rebase 清理 commits

写完一个 feature,你可能有一堆 WIP commits:

* a1b2c3 WIP
* d4e5f6 more
* 789abc fix typo
* def012 feat(anchor): add verification logic

PR 前清理成一个清晰的 commit:

git rebase -i HEAD~4
# 编辑器会打开,把后三个改成 "fixup" 或 "squash"

结果:

* xyz789 feat(anchor): add verification logic with three-level fallback

清爽了。PR review 的人不用在 WIP 里翻。

动作 8:定下 merge 策略

R·Agent 推荐:Squash and merge(GitHub 按钮上的选项)。

理由:

场景 Merge Commit Rebase and Merge Squash and Merge
main 历史是否线性 ❌ 有合并提交 ✅ 线性 ✅ 线性
保留 feature 分支细节 ✅ 全保留 ✅ 全保留 ❌ 压成一个
git bisect 体验 差(容易踩到合并提交) 好 好
回滚一个 feature 难(多个 commit) 难 ✅ 一个 revert 搞定
小团队推荐 中 中 ✅ 强烈推荐

为什么 Squash 适合你:PR 里的 10 个 “WIP” commits 是 feature 分支的内部事务,合到 main 后只需要看到”加了 anchor verification”这一件事。出问题了,git revert <squash-commit> 一键回滚整个 feature。

💡 术语小词典 - git bisect:二分查找 bug 的神器。用法:告诉 git “v1.0 的时候好的,v1.5 坏了”,git 会自动 checkout 到中间那个 commit,你测一下,告诉 git 好还是坏,git 继续二分,直到定位到第一个引入 bug 的 commit。前提:每个 commit 都能编译 + 运行。这就是为什么 squash 策略下 bisect 体验好 —— 每个 main 上的 commit 都是完整的 feature,不会踩到”半成品 WIP commit”。 - git revert:反向撤销一个 commit。它不是删除历史,而是生成一个新 commit 来抵消旧 commit 的效果。适合已经 push 到 main 的情况(因为不改历史,安全)。Squash 策略下一个 feature 就是一个 commit,所以一次 revert 就能撤销整个 feature。

🟢 1.5.3 新建分支做 feature

标准流程(每次开始一个新任务都走这一遍):

# 1. 先切回 main,确保自己在"干净的起点"
git checkout main

# 2. 拉远程最新代码(否则你的分支会基于老 main)
git pull origin main

# 3. 基于 main 创建新分支 + 切过去(一条命令搞定)
git checkout -b feature/anchor-verify

# 4. 开始写代码...

# 5. 写完一部分,阶段性提交
git add src/anchor_verify.py
git commit -m "feat(anchor): add basic verification logic"

# 6. 推到远程(第一次推要加 -u 建立跟踪)
git push -u origin feature/anchor-verify

💡 -u / --set-upstream 是干嘛的? 第一次 push 新分支时加 -u,告诉 git:“我这个本地分支以后就跟远程那个分支绑定了。” 绑定之后,你可以直接 git push / git pull 不用指定分支名。不加 -u 也能 push,但以后每次都得打全名。

🟢 1.5.4 看别人在干啥 · fetch vs pull

这是你最容易混淆的一组命令。记住一句话:

fetch 是”看”,pull 是”看 + 抄过来”

graph TB
    subgraph "你的电脑"
        L[本地 main<br/>你实际工作的分支]
        OM[origin/main<br/>你本地"对远程的印象"]
    end
    
    subgraph "GitHub"
        RM[远程 main<br/>真实状态]
    end
    
    RM -->|fetch: 只更新印象| OM
    OM -->|merge 或 rebase: 抄到实际分支| L
    RM -->|pull = fetch + merge| L
    
    style L fill:#fef3c7
    style OM fill:#dbeafe
    style RM fill:#dcfce7

两者的差别:

命令 做什么 安全吗? 用在什么时候
git fetch origin 只更新”本地对远程的印象”(origin/main 这个指针) ✅ 非常安全,不动你正在工作的文件 想知道别人最近推了啥,但不想打扰自己
git pull origin main fetch + 把变更 merge 进你当前分支 ⚠️ 可能产生冲突 你确定要把远程更新拉到本地工作

推荐的日常用法:

# 场景 A:我想看看别人推了什么,但不想立刻合并
git fetch origin
git log origin/main ^HEAD --oneline   # 列出远程有但本地没有的 commit

# 场景 B:我要开始干活了,需要最新的 main
git checkout main
git pull origin main

# 场景 C:我的 feature 分支落后了,想同步 main
git fetch origin
git rebase origin/main      # 私有分支用 rebase,历史干净
# 或
git merge origin/main       # 保守派,生成 merge commit

💡 origin/main 和 main 的区别 - main = 你本地实际在用的分支 - origin/main = git 在本地缓存的”远程 main 最后一次被我 fetch 到的样子” - 这是两个独立的指针。你 git fetch 只更新后者,不动前者。所以 fetch 永远不会影响你正在编辑的文件。

🟡 1.5.5 合并别人的代码 · 三种姿势

场景:队友写完了 feature/docx-parser,你想在自己本地测试一下再 merge

# 1. 拉队友的分支到本地
git fetch origin
git checkout -b feature/docx-parser origin/feature/docx-parser
# 或更短:
git checkout feature/docx-parser   # 如果本地没有,git 会自动追踪远程

# 2. 测试...
pytest tests/

# 3. 切回你自己的分支,合并他的
git checkout feature/anchor-verify
git merge feature/docx-parser

怎么看要合并的内容是什么?(你明确列的痛点)

# merge 前预览:我当前分支合并对方后,会多哪些 commit?
git log HEAD..feature/docx-parser --oneline

# 预览会改哪些文件?
git diff HEAD..feature/docx-parser --stat

# 预览具体改了什么代码?
git diff HEAD..feature/docx-parser

# 更直观的三方对比(适合看冲突可能发生在哪)
git diff HEAD...feature/docx-parser

💡 .. 和 ... 的差别(老手也常搞混) - A..B = “在 B 但不在 A 的 commit”(常用) - A...B = “两个分支各自独有的 commit,不包括共同祖先”(适合看”从分叉点以来,两边各走了多远”)

记忆法:两个点是单向,三个点是双向。

🟡 1.5.6 解冲突 · 最高频的协作痛点

冲突是怎么产生的?

你和队友都改了 src/normalize.py 的第 42 行。git 不知道该听谁的,让你手动解决。

冲突标记长什么样?

def normalize_text(raw: str) -> str:
<<<<<<< HEAD
    # 我的版本:用 replace 实现
    return raw.replace("\r\n", "\n").replace("\\n", "\n")
=======
    # 队友的版本:用正则实现
    return re.sub(r"\r?\n|\\n", "\n", raw)
>>>>>>> feature/docx-parser

三段的含义: - <<<<<<< HEAD 到 ======= = 你当前分支的版本 - ======= 到 >>>>>>> = 你要合并进来的分支的版本 - >>>>>>> feature/docx-parser = 告诉你这个版本从哪来

解决流程(四步):

# 1. 找出所有冲突文件
git status
# Unmerged paths:
#   both modified: src/normalize.py

# 2. 打开文件,人工决定留哪个(或者两个都留,或者写第三个版本)
# 把 <<<<<<< ======= >>>>>>> 这三行标记全部删掉

# 3. 标记为已解决
git add src/normalize.py

# 4. 继续未完成的操作
git merge --continue      # 如果在 merge 中
git rebase --continue     # 如果在 rebase 中

VS Code 里的更好体验:

VS Code 遇到冲突会显示三个按钮:Accept Current Change / Accept Incoming Change / Accept Both Changes。但最重要的按钮是”Compare Changes” —— 它并排展示两个版本,你能清楚看到差别。建议永远先点 Compare 再决定。

什么时候该中止?

如果冲突太多太乱,别硬解:

# 放弃这次 merge/rebase,回到操作前的状态
git merge --abort
git rebase --abort

然后跟队友语音对一下,商量出合并策略再来。

🟡 1.5.7 只更新某个文件或文件夹

场景:队友的 PR 已经合进 main,但你只想先拿他改的某一个文件到你的分支上用

# 只从 main 拉取某个文件到当前分支
git checkout main -- src/normalize.py

# 或者从另一个分支拉某个文件
git checkout feature/docx-parser -- src/parser/

# 这个操作会把文件放到暂存区(相当于已经 add 了),你可以直接 commit
git commit -m "chore: sync normalize.py from main"

警告:这是危险但有用的技术。风险是 —— 你只拿了一个文件,但这个文件可能依赖了其他你没拿的改动。适用场景:

  • ✅ 拿一个独立工具脚本
  • ✅ 拿一份更新后的配置文件
  • ❌ 拿一个跟其他模块紧耦合的代码文件

🟡 1.5.8 维护远端 main 分支 · 作为 PO 的职责

作为 PO,你可能不是每天写代码的人,但你对 main 分支的”干净度”负责。以下是每周要做的事:

每周 1 · 检查 main 的健康状态

git checkout main
git pull origin main
git log --oneline --since="1 week ago"    # 本周合并了什么

看一遍有没有不规范的 commit 消息(意味着 commitlint 没拦住,规则有漏洞)。

每周 2 · 清理已合并的 feature 分支

# 列出所有已经合进 main 的分支(可以删了)
git branch --merged main

# 本地删除
git branch -d feature/old-done-feature

# 远程删除
git push origin --delete feature/old-done-feature

# 一次性清理远程已删除但本地还留着的分支引用
git fetch --prune

每月 · 打一个版本 tag

# 查看现有 tag
git tag -l

# 打一个带说明的 tag(推荐用 annotated tag)
git tag -a v0.3.0 -m "R·Agent v0.3.0: anchor verification + L2 fallback"

# 推到远程
git push origin v0.3.0

推 tag 之后,GitHub 会自动生成一个 Release 页面,你可以在上面写 release notes。配合 Conventional Commits,甚至可以用工具(standard-version、semantic-release)自动生成 changelog。

🔴 1.5.9 救命场景 · 我改坏了怎么办?

git 的所有操作几乎都是可逆的,只要你知道怎么找回来。

场景 A:我改了文件但还没 add,想全部丢弃

# 丢弃单个文件的改动
git restore src/normalize.py

# 丢弃所有未 add 的改动(小心,不可逆)
git restore .

场景 B:我 add 了但还没 commit,想取消 add

git restore --staged src/normalize.py     # 从暂存区移回工作区(内容还在)

场景 C:我刚 commit 了但发现消息写错了

git commit --amend -m "feat(anchor): 正确的消息"

前提:这个 commit 还没 push,或者只推到了你独占的私有分支。

场景 D:我刚 commit 了,但其实有个文件忘了包括

git add src/forgot-this.py
git commit --amend --no-edit     # 追加到上一个 commit,不改消息

场景 E:我 commit 了三次,想撤销最后一次但保留改动

# 指针回退一格,改动保留在工作区
git reset --soft HEAD~1
# 现在相当于这些改动回到"已 add 未 commit"状态

场景 F:终极救命 · git reflog

git 几乎永远不会真的丢东西。就算你 reset --hard 了,被”丢弃”的 commit 还在 reflog 里躺着。

# 看过去 30 天所有的 HEAD 移动记录
git reflog

# 输出示例:
# a3f2c1 HEAD@{0}: reset: moving to HEAD~3
# 789abc HEAD@{1}: commit: feat(anchor): ...  ← 这是被丢掉的!
# def012 HEAD@{2}: commit: WIP

# 恢复:
git reset --hard 789abc
# 或
git checkout -b recover-branch 789abc

💡 reflog 是你的保险带。只要在 90 天内(默认保留期),任何”丢失”的 commit 都能找回来。知道这点,你 git 操作会自信很多。

🔴 1.5.10 救命场景 · 有人 force push 了共享分支

症状:你早上一 pull,发现一堆冲突,而且你的 commit 似乎不见了。

大概率原因:昨晚有人在 main 上 git push --force(或 rebase 之后硬推),改写了历史。

应对:

# 1. 不要慌,你的 commit 还在 reflog
git reflog

# 2. 找到你昨天最后一个本地 commit 的 hash
# HEAD@{5} 可能就是你昨晚干活的地方

# 3. 基于那个 commit 建一个保险分支
git branch emergency-backup HEAD@{5}

# 4. 强制重置本地 main 到现在的远程
git fetch origin
git reset --hard origin/main

# 5. 把你的 commit 从保险分支 cherry-pick 回来
git cherry-pick <your-commit-hash>

然后,立刻跟团队开会说明:force push 到共享分支是最高优先级的事故,要定规矩(branch protection 开启 “do not allow force push”)防止再发生。

🔴 1.5.11 救命场景 · 提交了秘钥怎么办

最坏情况:你 push 了一个包含 API key 的 .env 文件到公共仓库。

立刻做(5 分钟内):

  1. 立刻到服务提供商那里作废这个 key。不是”先撤回 commit”,是先作废 key。因为从你 push 那一刻起,假设它已经泄露。
  2. 生成新的 key,更新本地 .env
  3. 把 .env 加入 .gitignore

然后再清理历史:

# 如果只是最后一个 commit 出错
git reset --soft HEAD~1
# 从暂存区撤掉 .env
git restore --staged .env
# 重新 commit
git commit -m "chore: add env template"
# 强制推送(这种情况下必要)
git push --force-with-lease origin <your-branch>

如果秘钥已经在历史深处,用 git filter-repo 或 BFG Repo-Cleaner 清理整个历史,然后全团队重新 clone。这种事故一旦发生,代价非常大。

预防措施(必做):

# 安装 pre-commit 框架,加一个秘钥检测 hook
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.4.0
    hooks:
      - id: detect-secrets

配完这个,你根本没机会把秘钥 commit 进去。

1.6 行业权威怎么做

Atlassian 的官方立场

Atlassian 同时维护 Git Flow 和 Trunk-Based Development 两套文档。他们的结论:

“Trunk-based development is a version control management practice where developers merge small, frequent updates to a core trunk or main branch…Gitflow is an alternative Git branching model that uses long-lived feature branches and multiple primary branches. Gitflow has more, longer-lived branches and larger commits than trunk-based development.”

中文解读:Atlassian 明确区分了两个场景 —— 持续部署选 trunk-based,有调度发布的企业环境选 Gitflow。没有中立意见,是按场景选。

Gitflow 作者 Vincent Driessen 的反思

2020 年,Gitflow 的发明者 Vincent Driessen 在自己的博客里加了一段声明。Assembla 引述:

“‘(…)the most popular type of software that is being developed with Git is shifting more towards web apps – at least in my bubble. Web apps are typically continuously delivered, not rolled back, and you don’t have to support multiple versions of the software running in the wild.’”

翻译:Gitflow 的发明者自己承认,2010 年那套规则是为”需要同时维护多个版本”的软件设计的。对 web 应用和持续部署场景,不适用。

对你的启示:不要盲目抄大公司的 git flow,要看你的场景匹配不匹配。

arXiv 2025 年的实证研究

“Our results indicate that trunk-based development favors fast-paced projects with experienced and smaller teams, while branch-based development suits less experienced and larger teams better, despite posing management challenges.”

简明结论:团队小 + 经验足 → trunk-based;团队大 + 经验不一 → branch-based(Git Flow 或 GitHub Flow)。

R·Agent 团队小但经验不一(有 AI 新手),所以推荐 GitHub Flow —— 比 trunk-based 多一层 PR 保护,比 Git Flow 少几层分支负担。

一个有争议的业界实践

关于 merge vs squash,业界有激烈争论。来自 HashiCorp 工程经理 Mitchell Hashimoto 的观点:

“I prefer merge and creating a merge commit because I think it best represents true history. You can see the merge point, you can see all the WIP commits the developer went through. You can revert the whole merge easily (git revert -mN). I create merge commits more than 9 out of every 10 PRs.”

翻译:他更喜欢 merge commit,理由是”保留真实历史”。这跟我们的 squash 推荐不一样。

为什么我还是推荐 squash?他的场景是 OSS + 大型专业团队,每个开发者能保证”每个 commit 都能编译”。你团队做不到这一点(AI 生成的中间 commit 经常是半成品)。Squash 更适合你。

1.8 学会检验 · 你能讲出来吗?

费曼原则:讲不出来就不算懂。

自检 1:你能用一句话讲清 git 分支是什么吗?

参考答案:“分支是一个指向某个 commit 节点的指针。创建分支只是新建了一个指针,不会复制文件;切换分支只是把工作区切换成那个指针指向的 commit 的状态。”

如果你说不出”指针”两个字,说明原理一你没真懂。

自检 2:你能解释为什么”不能在共享分支上 rebase”吗?

参考答案:“rebase 会改写 commit 历史(新生成一串 commit 节点)。如果这个分支是共享的,别人本地还指向旧节点,他下次 pull 会拉到诡异的’新旧节点并存’的状态,导致混乱甚至数据丢失。”

自检 3:你的团队小伙伴问你:我该用 rebase 还是 merge?你怎么答?

参考答案:“看你在哪里操作。在自己的私有 feature 分支上同步 main,用 rebase,让历史干净。在 PR 合入 main 时,用 squash and merge,把 feature 分支的一堆 WIP 压成一个有意义的 commit。永远不要在已经有别人 push 过的共享分支上 rebase。”

自检 4:一个 commit 消息 fix!: remove legacy API endpoints 对应什么版本变化?

参考答案:“MAJOR bump。fix 本来只会触发 PATCH,但带了 ! 表示 BREAKING CHANGE,按 SemVer 规则,任何破坏向后兼容的变更都触发 MAJOR bump。”

自检 5:PR 的 branch protection 为什么要开 ‘Do not allow bypassing’?

参考答案:“这条规则让管理员也不能绕过。否则 PO 或技术负责人可以直接 push 到 main,审计链就断了。医疗器械法规场景下,’管理员特权绕过’就是合规风险 —— 你说不清楚这段代码到底有没有 review。”

自检 6:你能跟工程师用他的语言讨论 Git Flow vs GitHub Flow 的取舍吗?

参考答案(模拟对话):

工程师:“我们要不要上 git-flow?”

第 2 章 · LLM Pipeline 的解耦设计

从 12 个按钮到一套可控的流水线

本章目标:让你能清楚识别自己 pipeline 里的每一个”作用点”、它对指标的影响、怎么把相互污染的作用点切成独立可控的按钮。学完你可以跟工程师说:“质量这次下降,主要是 Stage 1 的表格分流贡献了 70%,跟 prompt 无关,不用动 LLM。”

2.1 痛点切入 · 你真实的一段话

你跟我说过这样一段话:

“大语言模型的输出部分,它其实和好几个地方相关:

1. 和 Prompt 本身有关,因为 LLM 的内容本身就是 Prompt 2. 和 LLM 里的前置处理、后置处理有关 3. 和前上游的 Stage 0 和 Stage 1 相关,涉及抓取、对齐等操作 4. 和 Table 及表格的分流处理有关

所以每一个环节其实相互之间都会有作用。因此,如果你要测试一个性能,其实要追着去看。包括它生成的效果,如果一个不好,或者说表格解析有问题,我就只能在 LLM 里面不断地加静态方法去补足这个操作。”

这段话里,有三个致命信号:

  • “要追着去看” —— 说明 pipeline 不可调试
  • “只能在 LLM 里面不断地加静态方法” —— 说明你在被迫打补丁
  • “每一个环节相互之间都会有作用” —— 说明没有真正的解耦

这不是你写得不好。这是任何 LLM pipeline 在不做解耦设计的情况下的必然结局。

把这段话画成图,叫”污染链”

想调”LLM 输出质量”这个指标,你现在面对的现实:

┌──────────────────────────────────────────────────┐

  • 4 个影响因素(prompt / 前处理 / 后处理 / 上游数据)
  • 3 个调 LLM 的 Stage(Stage 2 / Stage 3 / Stage 4)

  • ✅ 不再往 LLM 里加静态方法补足 —— 因为静态方法会有它专属的位置
  • ✅ Stage 之间物理切开 —— 改 Stage 1 不影响 Stage 2
  • ✅ 任何一次实验都能独立测量贡献 —— “这次改动把整体质量推高了 3 个点,全部来自 Stage 3 的 prompt”
  • ✅ 换 LLM 的成本降到一天以内

2.2 费曼式核心 · 解耦的 3 个底层原理

原理一:单一变量原则(Single Variable Rule)

这是实验科学的底层方法论,直接搬到工程上:

一次只改一个变量,你才能知道是这个变量导致了效果变化。

你现在加静态方法的那一刻,其实同时改了: - LLM 的输入(prompt 变了) - LLM 的输出处理(后处理逻辑变了) - 下游的数据(被改后的输出进入 Stage 3)

三个变量同时变,效果好了你归因不了,效果差了你也不知道哪变量是元凶。

实际操作里的体现:

❌ 错误做法(改多个变量):
   改 Stage 2 的 prompt + 加一个静态方法 + 微调 Stage 3 的输入

✅ 正确做法(改一个变量):
   只改 prompt → 跑整个 pipeline → 记录指标变化
   再只加静态方法 → 跑整个 pipeline → 对比刚才的指标
   再只微调 Stage 3 → ...

代价:跑的次数多。收益:你真的知道哪个变量起了多大作用。对 LLM pipeline 这种本来就难调的系统,不做单一变量,就是瞎试。

💡 术语小词典:A/B 测试 vs 消融实验(ablation study) - A/B 测试:两个版本并行对比(A 方案 vs B 方案),看哪个指标好 - 消融实验:“去掉某一块”看效果差多少,用来度量每一块的贡献。原本常用于深度学习,但特别适合 LLM pipeline - 你应该主要做消融 —— 比如”去掉这个后处理,指标降多少?“,能量化后处理的价值

原理二:物理边界决定逻辑边界(Physical = Logical)

这条原理更深刻。你记这一句话:

如果两个阶段在物理层面没有边界,它们在逻辑层面就不会有边界。

什么叫物理边界?两个阶段之间有一个可以被独立读写的东西。不一定是文件,也可以是数据库表、消息队列。但必须是”一个阶段写完它,另一个阶段从它开始读”。

反面例子(你现在大部分 Stage 之间是这样):

# 在 lefa.py 里
stage1_output = run_stage1(input_data)       # 内存里的 dict
stage2_output = run_stage2(stage1_output)    # 直接传 dict
stage3_output = run_stage3(stage2_output)    # 继续传

表面上 Stage 1、2、3 是三个函数,看起来解耦了。实际上耦合得像一个函数。证据:

  • 不能单独重跑 Stage 2 —— 要重跑必须从 Stage 1 开始
  • 不能单独测 Stage 2 —— 因为你不知道 Stage 1 会产出什么 dict
  • Stage 1 改了数据结构 —— Stage 2 静默地跟着挂
  • 想对比两个 Stage 2 版本 —— 必须跑整个 pipeline 两次

正面例子:

# 在 lefa.py 里
run_stage1(input_data, out="stage1_out.csv")
run_stage2(in_="stage1_out.csv", out="stage2_out.csv")
run_stage3(in_="stage2_out.csv", out="final.json")

这三行看起来啰嗦,但它带来了质变:

  • ✅ 可以用手工伪造的 stage1_out.csv 直接测 Stage 2
  • ✅ Stage 1 已跑过,单独重跑 Stage 2(秒级,不用等 Stage 1 的 LLM 调用)
  • ✅ 把 stage1_out.csv 存一份,你永远有”Stage 1 的基准产出”可对比
  • ✅ Stage 1 的人和 Stage 2 的人可以并行开发,只要约定 CSV 格式

一句话总结原理二:

把阶段的输出”物化”成一个文件,是世界上最便宜的解耦技术。

💡 术语小词典:中间态物化(Materialization) - 物化:把计算结果”实体化”到磁盘(或数据库),不再只活在内存 - 好处:每个阶段可以独立重跑、独立测试、独立替换实现 - 代价:磁盘 IO 多一点,但对 LLM pipeline 这种阶段本来就慢(一次 LLM 调用几秒)的场景,几十毫秒的文件 IO 完全可以忽略

原理三:可观测性决定可调试性(Observability = Debugability)

你说”如果一个不好,或者说表格解析有问题,我就只能追着看”。这句话的完整意思是:

你看不到中间到底发生了什么,所以只能猜。

可观测性 = 每一个阶段的输入、输出、中间决策都能被看到、能被重放、能被对比。

你做到了以下哪几件,决定你能多快定位问题:

能观测到的东西 代价 收益
每个 Stage 的输入输出被保存 几行代码 + 硬盘空间 出事能看
每次 LLM 调用的 prompt 和 raw response 被保存 几行代码 LLM “不正常”时能复盘
每个 Stage 的耗时和 token 数被记录 几行代码 性能瓶颈可定位
每次跑 pipeline 有一个 trace_id 贯穿 需要设计 一次问题的完整链路可还原
中间态数据能和”上一次”对比 需要版本化 退化时能指向哪个 Stage

没有可观测性的 pipeline,任何指标波动都变成玄学。你不知道今天的输出变差是因为 LLM 服务抖了,还是你改的代码引入的,还是输入数据本身就不一样。

原理三直接推出一条纪律:每个 Stage 结束时必须写出一个”我的输出是什么”的产物。这个产物就是原理二说的物化产物。

💡 可观测性的三个层次(越往下越贵越强) 1. Log(日志):文字流水,出事后翻。最便宜,最弱 2. Artifact(产物):每个 Stage 的输出文件,可重读、可对比。中等代价,很强 3. Trace(链路追踪):一次请求的完整链路,每个环节耗时、输入输出都能看。代价大,最强

对你现在的 Lefa 而言,先做好 Artifact 就够了。Log 是自然结果,Trace 是半年后的事(在第 5 章展开)。

这张表最关键的三个设计决策

决策 1 · L2 只做”干净的 LLM 调用”,禁止在里面加静态方法

你现在把后处理嵌在 LLM 调用函数里。把它搬出来,独立成 L3 层。好处:

  • 你可以关掉 L3 跑一次,看 L2 原生输出是什么样 → 这是消融实验
  • 下游(L4 Q-Gate)能分别看到 L2 原始输出和 L3 修补后输出 → 可对比
  • 如果某个静态方法其实不再需要了,你能识别到”它没在修什么实际问题”,删掉
  • L2 可以独立替换(换 LLM 模型)而 L3 规则不动

决策 2 · Q-Gate(L4)是独立的一层,不是附加在某个 Stage 里的

你说”不同 Stage 之间还共享了一些 Evaluation”。把它命名、标准化,让它成为每个阶段边界上的独立组件。

Q-Gate 的职责只有三件:

  1. 校验输入数据符合契约(字段在不在、类型对不对)
  2. 校验业务规则(confidence 够不够、改动比例合不合理)
  3. 不通过时触发降级(sidecar / fallback / halt)

Q-Gate 不改内容。它只是”检查站”。改内容是 L3 的事。

决策 3 · L1 的”分流”是独立的,不要把它藏在 L2 LLM 调用里

把它独立出来:

def default_confidence_when_missing(parsed: dict) -> dict:
    """
    Rule: L2 有时漏 confidence 字段。
    Context: 2026-03-12 在 batch-142 首次发现。
    Applied when: confidence 不在 parsed 里
    Effect: 填 0.5 作为默认值(中等置信)
    """
    if "confidence" not in parsed:
        parsed["confidence"] = 0.5
    return parsed


def empty_markers_as_list(parsed: dict) -> dict:
    """
    Rule: markers 字段有时是 null,下游期望 list。
    Applied when: markers is None
    Effect: 替换为空 list
    """
    if parsed.get("markers") is None:
        parsed["markers"] = []
    return parsed


def coerce_position_to_int(parsed: dict) -> dict:
    """
    Rule: Claude 偶尔把 position 返回成 str。
    Applied when: 任一 marker 的 position 是 str
    Effect: 强制转 int
    """
    for m in parsed.get("markers", []):
        if isinstance(m.get("position"), str):
            m["position"] = int(m["position"])
    return parsed


def truncate_long_summary(parsed: dict) -> dict:
    """
    Rule: summary 过长会破坏 UI 显示。
    Applied when: summary 超过 500 字符
    Effect: 截断到 500
    """
    if len(parsed.get("summary", "")) > 500:
        parsed["summary"] = parsed["summary"][:500]
    return parsed

每条规则一个函数,每个函数有 docstring 说明”修什么 / 为什么修”。这不是代码洁癖,是为未来的你保留决策历史。

import logging

log = logging.getLogger(__name__)

POSTPROCESS_RULES: list[Callable[[dict], dict]] = [
    default_confidence_when_missing,
    empty_markers_as_list,
    coerce_position_to_int,
    truncate_long_summary,
]


def apply_postprocessing(parsed: dict, trace_id: str = None) -> tuple[dict, list[str]]:
    """
    顺序应用所有 L3 规则,返回 (修补后的结果, 触发了哪些规则)。
    """
    original = parsed.copy()
    triggered = []
    
    for rule in POSTPROCESS_RULES:
        before = parsed.copy()
        parsed = rule(parsed)
        if parsed != before:
            triggered.append(rule.__name__)
            log.info(
                "postprocess.rule_triggered",
                extra={"rule": rule.__name__, "trace_id": trace_id}
            )
    
    return parsed, triggered

import json
from datetime import datetime
from pathlib import Path

class ArtifactStore:
    def __init__(self, run_id: str = None):
        self.run_id = run_id or datetime.now().strftime("%Y%m%d_%H%M")
        self.dir = Path(f"artifacts/run_{self.run_id}")
        self.dir.mkdir(parents=True, exist_ok=True)
    
    def save(self, name: str, data: dict | list):
        path = self.dir / f"{name}.json"
        path.write_text(json.dumps(data, ensure_ascii=False, indent=2))
        return path
    
    def load(self, name: str) -> dict | list:
        path = self.dir / f"{name}.json"
        return json.loads(path.read_text())

动作 3:给每个 Stage 的输入输出定义 Schema

注意:schema 不是主角。它是为了让”中间态物化”有一个形式化的契约,防止下一次 Stage 2 产出了跟上一次结构不一样的东西。

# src/contracts/stage_schemas.py
from typing import TypedDict, Literal, NotRequired

class Stage1Output(TypedDict):
    """Stage 1 分流层的输出契约。"""
    text_chunks: list[str]
    table_chunks: list[dict]
    mixed_chunks: NotRequired[list[dict]]
    routing_metadata: dict


class Marker(TypedDict):
    position: int
    label: str
    confidence: float


class Stage2LLMRawOutput(TypedDict):
    """Stage 2 的 L2 原生输出(从 LLM 出来还没修补)。"""
    markers: list[Marker] | None    # 可能是 None,后面靠 L3 规则修
    confidence: NotRequired[float]  # LLM 偶尔漏
    summary: str


class Stage2FinalOutput(TypedDict):
    """Stage 2 的 L3 修补后输出(下游真用的)。"""
    markers: list[Marker]           # 保证是 list
    confidence: float               # 保证存在
    summary: str                    # 保证 <= 500 字

为什么要分 Raw 和 Final 两个 schema?

这是第二章最架构师味道的一个设计 —— 用 schema 表达”L2 不保证的东西 vs L3 保证的东西”。

  • Raw schema 里 markers 是 list | None(LLM 可能返回 null)
  • Final schema 里 markers 一定是 list(因为 L3 的 empty_markers_as_list 规则修过了)

这让你看 schema 就知道 L3 每条规则修什么。

💡 Raw/Final 两段式 schema 是一种架构表达 这个模式在 dbt(数据工程工具)里叫 “staging → final” 模式。阶段性输出用 staging schema(宽松),最终稳定输出用 final schema(严格)。

动作 5:Q-Gate 标准化,单独成层(L4)

# src/qgates/base.py
from typing import Callable, Literal

QGateResult = Literal["pass", "warn", "fail"]

class QGate:
    def __init__(self, name: str, level: Literal["strict", "lenient"]):
        self.name = name
        self.level = level
    
    def check(self, data: dict) -> tuple[QGateResult, str]:
        raise NotImplementedError


class SchemaQGate(QGate):
    """校验数据符合 TypedDict 契约。"""
    def __init__(self, name: str, schema_type):
        super().__init__(name, "strict")
        self.schema_type = schema_type


class ThresholdQGate(QGate):
    """校验数值指标达到阈值。"""
    def __init__(self, name, field: str, min_value: float):
        super().__init__(name, "lenient")
        self.field = field
        self.min_value = min_value
    
    def check(self, data):
        value = data.get(self.field, 0)
        if value < self.min_value:
            return "warn", f"{self.field}={value} < {self.min_value}"
        return "pass", ""

最大的好处:所有质量问题都有一份标准化的报告,出问题时一眼定位,不用”追着看”。

- 最终质量:                     0.87 → 0.78

结论:质量下降主要是 Stage 0 出问题了,跟 LLM 和 prompt 无关。

🟢 2.5.3 L3 规则什么时候该加 / 该删

加的条件(三个都满足): 1. 出了一个具体的 bug 2. 这个 bug 是 LLM 行为导致的 3. 规则能清晰表达(if this then that)

删的条件(满足一个就考虑): 1. 连续一个月零触发 2. 消融实验显示去掉无影响 3. LLM 模型升级了,旧 bug 理论上已修

永远不加的规则: - ❌ “如果结果不太对,就硬改成我想要的”(这是幻觉修正,应该改 prompt) - ❌ “如果缺某个字段,就调 LLM 再问一次”(流程问题,应改 L2)

🟡 2.5.4 换 LLM 怎么办

如果你做对了上面的所有动作,换 LLM 是一天的工作。

需要改的: - L2 的 claude.call(prompt) → openai.call(prompt),就这一行 - prompt 可能要微调 - L3 的规则表可能需要更新

2.6 行业权威怎么做

Unix Pipe 哲学(1970s)—— 解耦思想的源头

Doug McIlroy 在设计 Unix pipe(|)时立下的设计原则:

“Write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface.”

翻译到你的 Lefa: - 每个 Stage 做一件事,做好 - Stage 之间通过通用接口(比如 JSON 文件)协作 - 文本/JSON 是通用接口,内存 Python 对象不是

Airflow 的 DAG 模式

Apache Airflow 用”有向无环图”描述 pipeline,每个节点是一个 task,边是数据依赖:

  • 每个 task 独立运行,输入输出都在外部存储
  • task 之间只传递引用(文件路径 / 表名),不传内存对象
  • task 失败可以单独重试,不影响上下游

dbt 的 Staging → Final 模式

dbt 规定了数据清洗的标准模式:

  • staging 层:原始数据的最小清洗,不做业务判断
  • intermediate 层:连接、聚合等业务逻辑
  • mart 层:最终产物,给业务用户

映射到 LLM pipeline: - L2 原生输出 = staging(LLM 说什么就是什么) - L3 修补 = intermediate(按规则清洗) - L4 Q-Gate 通过后的输出 = mart(给下游用)

Netflix 的 Metaflow · ML Pipeline 的中间态哲学

“Every step of a machine learning pipeline should be resumable and independently debuggable. This requires materialization of all intermediate artifacts.”

翻译:ML pipeline 的每一步都应该能单独恢复和调试,这要求所有中间产物物化。

有争议的:完全物化 vs 流式传递

支持完全物化(dbt / Airflow / Metaflow):可调试性第一,磁盘便宜 反对阵营(Kafka / Flink 流式):低延迟,实时系统

对你的 Lefa:你是批处理系统,完全物化是对的。

2.8 学会检验 · 你能讲出来吗?

自检 1 · 用一句话讲清楚”为什么要做中间态物化”

参考答案:“因为物理边界决定逻辑边界。如果两个 Stage 之间只在内存里传 dict,它们看起来像两个函数,实际上耦合得像一个 —— 不能独立重跑、不能独立测、不能对比两次产出。落盘后,每个 Stage 都变成可独立测试、可独立替换、可历史对比的单元。”

自检 2 · 你 Lefa 里 L2 和 L3 应该分别做什么?

参考答案:“L2 是 LLM 纯净调用层,只做 prompt 构造、单次 LLM 调用、JSON 解析。不允许任何 ‘静态方法补足’。L3 是规则化后处理层,每个 ‘静态方法’ 都拆成一个独立命名的 rule 函数,放在 L3 模块里。每次跑 pipeline 会产出 L2 原生输出和 L3 修补后输出两份文件,可以对比、可以消融实验。”

自检 3 · 你的同事说”我又在 LLM 调用里加了个小修复”,你怎么回应?

参考答案:“先问两个问题 —— 这是在修一个具体的 LLM bug 吗?还是在修 prompt 逻辑不够清晰的问题? 如果是后者,应该改 prompt 不是加修复。

如果确实是修 LLM bug,请把它抽出来成一个独立 rule 函数,放 L3,加 docstring 说明 ‘修什么、什么时候出现的、为什么’。这样我们下个月能知道它还有没有触发,必要时可以删。”

自检 4 · 最终指标下降了,怎么定位原因?

参考答案:“不要从 LLM 的 prompt 开始看。正确顺序:

  1. 跑 compute_attribution,对比今天和上周的每个 Stage 健康度,找退化最严重的
  2. 看那个 Stage 的中间态文件,对比今天 vs 上周
  3. 如果 Stage 0/1 健康度正常,才轮到看 Stage 2/3 的 L3 规则触发频率是否异常
  4. 最后才查 prompt 和 LLM 版本

这套流程把定位时间从小时级降到分钟级。”

自检 5 · 换 LLM 供应商,你 Lefa 哪些代码要改?

参考答案:“只改 L2 的 API 调用,就一行。可能要做的: - Prompt 适配(不同模型风格不一样) - L3 规则表可能要更新 - 重跑 attribution 报告,确认换后整体质量不退

不需要改的:Stage 0/1、L3 框架、L4 Q-Gate、L5/L6 输出。”

自检 6 · 跟一个架构师解释你的 Lefa

参考答案(模拟对话):

架构师:“你们 LLM pipeline 怎么设计的?”

你:“7 层,从 L0 摄取到 L6 输出。每层职责单一,L2 只做纯净 LLM 调用,L3 是规则化后处理层,每条规则独立函数可追踪可消融。层间数据走 artifact store 落盘,每次运行有独立 run_id,所有中间态可重读可对比。”

架构师:“指标出问题怎么定位?”

你:“先跑 attribution 报告,比较各 Stage 健康度,定位退化位置。再看 L3 规则触发频率。最后才查 prompt 和模型。几乎不用’追着看’。”

架构师:“架构上有什么取舍?”

你:“为了可调试性,我们做了完全物化 —— 每个 Stage 输出都落盘。代价是磁盘 IO 和存储,但对批处理场景完全可接受。参考了 dbt 的 staging→final 模式,Metaflow 的中间态哲学,Airflow 的 DAG 解耦原则。”

3.1 痛点切入 · 单脚本解决了,但 tool 还没有

第 2 章你把 Lefa 内部的 7 个 Stage 解耦了。L2/L3 分离,中间态物化,指标能归因。单脚本层面的问题解决了。

但 R·Agent 不只有 Lefa。你自己跟我说过:

  • Skill 包里放”纯抓取、解析、对齐”功能,被 Lefa 复用
  • 未来会有 Refa(另一个工作流),也要复用一部分 Skill
  • 有跨 Stage 调用的 Evaluation
  • 你想让 R·Agent 可以横向扩展到其他产品线(60% 基础设施复用)
  • CEO 层面的兴趣给了你做得大的可能 —— 意味着要多人协作、多工作流并存

这时候你会遇到一系列单脚本解耦解决不了的问题:

痛点 1 · 业务规则散落各处

假设 R·Agent 的核心业务规则是”confidence < 0.6 的 diff 必须人工复核”。这条规则现在在你代码里几个地方?

  • Stage 2 的 LLM 调用函数里(硬编码阈值)
  • Stage 3 的 Q-Gate(又出现一次)
  • Lefa 里的降级判断(再出现)
  • 可能还藏在 Skill 里某个函数

当业务方说”阈值改成 0.7”,你要改 4 处代码。漏改一处,pipeline 就出现”部分地方用 0.6 部分地方用 0.7”的诡异状态 —— 这种 bug 最难定位。

痛点 2 · 换 LLM 的成本不可预测

CEO 说:“我们评估一下用 Gemini 替代 Claude 的可行性。”

你得回答:改完要多久?需要重新测试多少东西?

现在的你可能答不上来 —— 因为 Claude 的调用散落在 Lefa、Skill、各种 util 函数里。你大概得: - 找到所有 claude.call(...) 的地方 → 可能 10+ 处 - 改 prompt 风格(不同模型偏好不一样) - 重新调整所有 L3 规则(新模型犯新的错) - 重新跑所有 integration test

这个成本不可预测 = 你没法跟 CEO 回答”一周 vs 一个月”。

痛点 3 · Lefa 和 Refa 之间将复制 80% 的代码

Refa 还没写,但你已经预感到:

  • Refa 会复用 Stage 0(PDF 摄取)
  • Refa 会复用 Stage 1 的分流
  • Refa 会复用 L3 后处理规则表
  • Refa 会复用所有业务规则(置信度阈值、降级策略)

怎么复用? 最直觉的做法是把 Refa 写成”Lefa 的一个大函数”,然后用一个 mode 参数切换。三个月后这个函数有 2000 行,包含各种 if mode == "lefa" else ... 分支。这就是经典的代码腐烂。

痛点 4 · AI 生成代码的”幻觉耦合”

这一点前面章节提过,这里再强调:

AI 会在你不知情的情况下,把业务逻辑慢慢渗透到 adapter 层。

你让 AI 写一个”从 docx 读段落”的函数,AI 可能顺手加上”如果段落 confidence < 0.6 就标红”—— 这一秒你没阻止,业务规则就漏到解析库里了。下次你想改阈值,得在解析库里改,这是反向依赖,越滚越乱。

3.2 费曼式核心 · Hexagonal 的 3 个底层原理

原理一:依赖反转 · 业务核心依赖抽象,而不是反过来

这是整个 Hexagonal 的灵魂。不理解这一条,后面都白学。

不好的架构(大多数初学者的写法):

Lefa(业务编排)
     ↓ import
Claude SDK(外部库)

看起来没毛病,但这意味着: - Lefa “认识” Claude。换 GPT 要改 Lefa - Lefa 的测试很难写(必须真调 Claude 或者 mock) - Claude SDK 版本升级,可能 break Lefa

Hexagonal 的做法:

Lefa(业务编排)
     ↓ 依赖
LLMClient(接口,你自己定义的)
     ↑ 实现
ClaudeAdapter(外部库的包装)
     ↓ import
Claude SDK(外部库)

注意箭头方向:Lefa 不再认识 Claude。Lefa 只认识一个叫 LLMClient 的抽象接口,这个接口是你自己定义的,写在你的 domain 里。ClaudeAdapter 负责”实现”这个接口。

💡 术语小词典 · 依赖反转(Dependency Inversion)

  • 反转的是什么?反转的是依赖方向。
  • 正向:高层业务 → 依赖 → 低层库(常见但是错的架构方向)
  • 反转:高层业务 → 定义抽象 ← 低层库实现这个抽象(Hexagonal)
  • 结果:业务不认识库,库认识业务接口

这是 SOLID 里的 D —— Dependency Inversion Principle(DIP)。

这条原理最重要的后果:LLM 供应商变成”可插拔”的。

# 换 Claude → GPT,只改一行配置
# config.py
LLM_ADAPTER = "ClaudeAdapter"  # 改成 "OpenAIAdapter"

# Lefa 代码一行不改

原理二:Driver vs Driven · 谁调我 vs 我调谁

Hexagonal 有一个术语容易混淆,但搞清楚会豁然开朗:

  • Driver Port(驱动端口) = 外界驱动你的入口。比如:HTTP API、CLI、UI
  • Driven Port(被驱动端口) = 你驱动外界的出口。比如:LLM、数据库、文件系统

你的 R·Agent 想象成一只六边形:

            ┌──── Driver ────┐
            ↓                ↓
         CLI              Web UI
            ↘              ↙
             ↘            ↙
          ┌─────────────────┐
          │                 │
          │   业务核心      │
          │   (Domain)      │
          │                 │
          └─────────────────┘
             ↙            ↘
            ↓              ↓
          LLM           Database
            ↑              ↑
            └─── Driven ───┘
  • Driver:从外面”戳”你的业务核心(CLI 命令、HTTP 请求、UI 按钮)
  • Driven:业务核心”戳”外面(调 LLM、存数据库、读文件)

两种 port 的实现位置:

Port 类型 接口定义在 实现(adapter)在
Driver Port domain(业务核心) 外部入口(entrypoints/)
Driven Port domain(业务核心) adapters/

对你的 R·Agent,目前: - Driver Port 可能就是 Lefa 的 main() 函数(CLI 方式) - Driven Port 会有好几个:LLM、docx 解析、文件存储、评估系统

💡 术语小词典 · Port 和 Adapter

  • Port(端口)= 抽象接口(Python 里用 Protocol 或 ABC 定义)
  • Adapter(适配器)= 这个接口的具体实现

一个 Port 可以有多个 Adapter:比如 LLMClient 这个 Port 可以有 ClaudeAdapter、OpenAIAdapter、MockAdapter(测试用)、CachedAdapter(加缓存)。业务核心完全不知道用的是哪个 adapter,它只和 port 打交道。

原理三:业务核心是”纯”的,adapter 才”脏”

什么是”纯” ? 在架构语境里:

  • 纯的代码:不依赖任何外部库(除了 Python 标准库和类型工具),可以在任何环境下跑、任何环境下测
  • 脏的代码:依赖外部系统(LLM、数据库、文件、网络),需要真实环境才能跑

Hexagonal 的主张:把”纯”和”脏”物理隔离。

示例对比:

# ❌ 不好的写法:纯和脏混在一起
def analyze_section(section_text: str) -> dict:
    # 脏:直接调 LLM
    response = anthropic.Client().messages.create(
        model="claude-4",
        messages=[{"role": "user", "content": section_text}]
    )
    raw = response.content[0].text
    parsed = json.loads(raw)
    
    # 纯:业务规则
    if parsed["confidence"] < 0.6:
        parsed["needs_review"] = True
    
    return parsed

这个函数无法测试(没有真 LLM 跑不起来),而且业务规则跟 LLM 供应商绑死(换 GPT 得改这个函数)。

# ✅ Hexagonal 写法:纯和脏分开

# domain/services.py - 纯
class SectionAnalyzer:
    def __init__(self, llm: LLMClient):  # 只依赖 port
        self.llm = llm
    
    def analyze(self, section_text: str) -> SectionAnalysis:
        raw = self.llm.generate(section_text)  # 通过 port 调
        parsed = self._parse_response(raw)
        
        # 业务规则
        if parsed.confidence < BusinessRules.MIN_CONFIDENCE:
            parsed.needs_review = True
        
        return parsed

# adapters/claude_adapter.py - 脏
class ClaudeAdapter(LLMClient):
    def generate(self, prompt: str) -> str:
        response = anthropic.Client().messages.create(...)
        return response.content[0].text

SectionAnalyzer 变成纯的: - 测试只要 mock 一个 LLMClient 就能跑,根本不需要真 LLM - 业务规则(阈值)在纯代码里,换 LLM 完全不影响 - 换 LLM 只改 ClaudeAdapter,domain 一行不动

💡 为什么”纯” > “脏”

不是”脏不好”,是脏的代码会污染一切。如果 domain 依赖了 Claude,那 domain 的测试需要 Claude,domain 的部署需要 Claude API key,domain 的 CI 需要网络。纯代码没有这些负担 —— 你可以把 domain 整包复制到火星上的飞船里都能跑。

核心概念

  1. 依赖方向:向内指向 domain,绝不向外
  2. Port 用 Protocol 定义(Python 3.8+,比 ABC 更 pythonic)
  3. Adapter 通过依赖注入传入:不在代码里 from xxx import claude
  4. Driver Port vs Driven Port:入口 vs 出口
  5. Fitness Function:CI 里自动检查架构边界

Python 实现工具

  • typing.Protocol:定义 port 接口(鸭子类型友好)
  • dataclasses 或 Pydantic BaseModel:domain models
  • import-linter:CI 里强制依赖方向
  • 依赖注入:手动注入或用 dependency-injector 库

  • ❌ Event Sourcing / CQRS —— 完全过度
  • ❌ 微服务拆分 —— 你是单体,不要硬拆
  • ❌ Spring / FastAPI 级别的 DI 框架 —— 手动注入更简单

动作 1:用 Protocol 定义你的第一个 Port

从 LLM 开始,因为这是最高 ROI 的一个。

# src/domain/ports/llm_client.py
from typing import Protocol


class LLMClient(Protocol):
    """LLM 调用的抽象接口。任何 LLM adapter 必须实现这个协议。"""
    
    def generate(self, prompt: str, **kwargs) -> str:
        """生成文本响应。
        
        Args:
            prompt: 输入 prompt
            **kwargs: 可选参数(temperature, max_tokens 等)
        
        Returns:
            raw text response,不做任何解析
        
        Raises:
            LLMError: 调用失败时
        """
        ...
    
    def generate_json(self, prompt: str, schema: type | None = None, **kwargs) -> dict:
        """生成结构化 JSON 响应。
        
        Args:
            prompt: 输入 prompt
            schema: 可选的 schema 约束(Pydantic model)
        
        Returns:
            parsed dict
        """
        ...

关键点: - Protocol 而不是 ABC。Protocol 是鸭子类型友好的 —— 任何有 generate 和 generate_json 方法的对象都自动”是” LLMClient,不需要 class ClaudeAdapter(LLMClient) 继承声明 - docstring 详细 —— 这是对所有 adapter 的”契约” - 没有 import anthropic / import openai —— domain 层禁止依赖任何外部 LLM 库

动作 2:写两个 Adapter 实现这个 Port

# src/adapters/llm/claude.py
import anthropic
import json
from src.domain.ports.llm_client import LLMClient


class ClaudeAdapter:
    """Claude 对 LLMClient port 的实现。"""
    
    def __init__(self, api_key: str, model: str = "claude-opus-4-7"):
        self.client = anthropic.Client(api_key=api_key)
        self.model = model
    
    def generate(self, prompt: str, **kwargs) -> str:
        response = self.client.messages.create(
            model=self.model,
            max_tokens=kwargs.get("max_tokens", 2000),
            messages=[{"role": "user", "content": prompt}],
        )
        return response.content[0].text
    
    def generate_json(self, prompt: str, schema=None, **kwargs) -> dict:
        # Claude 的 JSON mode 用 prompt engineering
        json_prompt = f"{prompt}\n\n请严格返回 JSON,不要有其他文字。"
        raw = self.generate(json_prompt, **kwargs)
        return json.loads(raw)

动作 3:把业务核心重写为纯代码

第 2 章你做过一次 L2/L3 分离。第 3 章把这个结果升级成 Hexagonal 标准结构:

# src/domain/services/section_analyzer.py
from dataclasses import dataclass
from src.domain.ports.llm_client import LLMClient
from src.domain.rules import BusinessRules
from src.domain.postprocess.markers import apply_postprocessing


@dataclass
class SectionAnalysis:
    """Section 分析结果 - domain model。"""
    section_id: str
    confidence: float
    markers: list[dict]
    needs_review: bool


class SectionAnalyzer:
    """纯业务服务 - 不依赖任何外部库。"""
    
    def __init__(self, llm: LLMClient, rules: BusinessRules):
        self.llm = llm
        self.rules = rules
    
    def analyze(self, section_text: str, section_id: str) -> SectionAnalysis:
        # L2:通过 port 调 LLM
        prompt = self._build_prompt(section_text)
        raw_response = self.llm.generate_json(prompt)
        
        # L3:规则化后处理(第 2 章的规则引擎)
        cleaned, _ = apply_postprocessing(raw_response)
        
        # 业务决策
        analysis = SectionAnalysis(
            section_id=section_id,
            confidence=cleaned["confidence"],
            markers=cleaned["markers"],
            needs_review=cleaned["confidence"] < self.rules.MIN_CONFIDENCE,
        )
        return analysis
    
    def _build_prompt(self, text: str) -> str:
        # prompt 模板也在 domain 里
        return f"分析以下内容并标注差异:\n{text}"

这个类的神奇之处:

  • 没有 import anthropic / openai —— 完全不知道用什么 LLM
  • 可以用 Mock 单元测试(秒级):SectionAnalyzer(MockLLMAdapter(), BusinessRules())
  • 换 LLM 只改构造函数的参数,类本身一行不改
  • 业务规则(MIN_CONFIDENCE)集中在 BusinessRules,不再散落

动作 4:把业务规则集中到 domain/rules.py

# src/domain/rules.py
from dataclasses import dataclass


@dataclass(frozen=True)
class BusinessRules:
    """R·Agent 的所有业务规则集中地。
    
    改这个文件需要 PO approve,因为它是跨 Stage 的通用规则。
    """
    
    # 置信度阈值
    MIN_CONFIDENCE: float = 0.6
    HIGH_CONFIDENCE: float = 0.85
    
    # 归一化阈值
    MAX_CHANGE_RATIO: float = 0.05
    
    # 降级策略
    L2_FALLBACK_ENABLED: bool = True
    L3_REVERT_ON_ANCHOR_FAIL: bool = True
    
    # 医疗器械合规阈值
    REQUIRE_MANUAL_REVIEW_BELOW: float = 0.6
    AUTO_APPROVE_ABOVE: float = 0.95
    
    @classmethod
    def from_yaml(cls, path: str) -> "BusinessRules":
        """从 business_rules.yaml 加载。"""
        import yaml
        with open(path) as f:
            data = yaml.safe_load(f)
        return cls(**data)

之后所有代码只能这样用:

# ✅ 对的用法
if analysis.confidence < self.rules.MIN_CONFIDENCE:
    ...

# ❌ 以后禁止的用法

    ...

效果:业务方说”阈值改成 0.7” → 你只改 rules.py 里的一行 → 全项目生效。

💡 术语小词典 · Fitness Function

架构社区给”在 CI 里自动检查架构规范”的做法起了个名字,叫 fitness function(来自 Neal Ford 《Building Evolutionary Architectures》)。import-linter 就是一种典型的 fitness function。

3.5 日常操作手册 · 按场景查

🟢 3.5.1 新加一个外部依赖,应该放在哪?

决策流程:

我要加的新功能,是否涉及"外部世界"?
  │
  ├── 调 LLM / 调外部 API / 读文件 / 写数据库 ──► adapter
  │       1. 先在 domain/ports/ 定义抽象接口
  │       2. 在 adapters/ 实现它
  │       3. domain 只 import port,不 import 具体实现
  │
  ├── 业务判断 / 算法 / 阈值 ──► domain
  │       在 domain/services 或 domain/rules 里
  │
  └── 编排、组装、配置 ──► app
          在 app/ 里

错误例子:“我在 domain 里用 pandas 处理数据” —— pandas 是外部库,domain 禁止。如果真要用,放 adapter 里包起来。

🟢 3.5.2 Lefa 和 Refa 怎么共享 80% 代码?

Lefa 和 Refa 都是 app 层,它们应该长这样:

🟢 3.5.3 “这段代码应该放哪?” 三分钟决策

每次写新代码前,问自己三个问题:

问题 1:这段代码能不能脱离 LLM、数据库、文件系统独立跑? - 能 → domain - 不能 → 继续问

问题 2:这段代码是外部库的包装,还是业务流程编排? - 包装外部库 → adapter - 编排流程 → app

问题 3:如果是业务逻辑,它是R·Agent 特有的还是某个工作流特有的? - R·Agent 特有(通用) → domain - 某个工作流特有 → app 里的那个工作流

# src/adapters/llm/openai.py
import openai
from src.domain.ports.llm_client import LLMClient


class OpenAIAdapter:
    def __init__(self, api_key: str, model: str = "gpt-5"):
        self.client = openai.Client(api_key=api_key)
        self.model = model
    
    def generate(self, prompt: str, **kwargs) -> str:
        response = self.client.chat.completions.create(
            model=self.model,
            messages=[{"role": "user", "content": prompt}],
            max_tokens=kwargs.get("max_tokens", 2000),
        )
        return response.choices[0].message.content
    
    def generate_json(self, prompt: str, schema=None, **kwargs) -> dict:
        # OpenAI 支持 json mode
        response = self.client.chat.completions.create(
            model=self.model,
            messages=[{"role": "user", "content": prompt}],
            response_format={"type": "json_object"},
        )
        import json
        return json.loads(response.choices[0].message.content)

🔴 3.5.6 救命:import-linter 挂了怎么办?

症状:PR 里 CI 挂了,错误是 Contract BROKEN: Domain must not depend on adapters

找到违规的 import:错误信息会直接告诉你,比如 src.domain.services.section_analyzer imports src.adapters.llm.claude

不要绕过 CI,做正确的修复:

方案 1(最常见):把依赖反转过来 - 旧代码:from src.adapters.llm.claude import ClaudeAdapter - 新代码:from src.domain.ports.llm_client import LLMClient - 把 ClaudeAdapter 通过构造函数注入,不在 domain 里 import

方案 2:这段代码本来就不该在 domain 里,移到 app 层

方案 3(紧急且极少用):暂时允许违规,但加 TODO

# 临时豁免,必须在 1 周内修复,issue #xxx
[importlinter:contract:1]
ignore_imports =
    src.domain.services.section_analyzer -> src.adapters.llm.claude

🔴 3.5.7 救命:AI 把业务逻辑悄悄写进了 adapter

症状:code review 发现 adapters/llm/claude.py 里出现了 if confidence < 0.6 这样的业务判断

为什么要救:这是典型的反向污染 —— 业务规则漏进了 adapter。下次改阈值,你可能漏掉 adapter 里的这处。

重构方法:

# ❌ 污染版
class ClaudeAdapter:
    def generate_json(self, prompt: str, **kwargs) -> dict:
        raw = self.generate(prompt)
        parsed = json.loads(raw)
        if parsed.get("confidence", 0) < 0.6:  # ← 业务规则漏到这
            parsed["needs_review"] = True
        return parsed

# ✅ 纯净版
class ClaudeAdapter:
    def generate_json(self, prompt: str, **kwargs) -> dict:
        raw = self.generate(prompt)
        return json.loads(raw)  # adapter 只做调用和 parse
# 业务判断回到 SectionAnalyzer (domain) 里做

预防:import-linter 抓不到这种(没有 import 违规),但code review 时要专门检查 adapter 里有没有 if 分支涉及业务阈值。第 6 章 CI 会讲怎么用静态分析抓这种。

3.6 行业权威怎么做

Alistair Cockburn 的原论文(2005)

Hexagonal Architecture 发明人 Alistair Cockburn 在 2005 年的原论文里说:

“Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases.”

翻译:让应用能被用户、程序、测试脚本或批处理任意驱动,能在脱离真实运行环境和数据库的情况下开发和测试。

这正是你要的 —— Lefa 能脱离真实 LLM 调用来测试,能换 LLM 不改业务代码。

AWS 官方 Python Hexagonal 模板

AWS Prescriptive Guidance 给了一个 Python Hexagonal 的官方目录结构,几乎跟本章一样:

├── adapters/
├── entrypoints/      # Driver 入口
├── domain/
│   ├── ports/
│   ├── model/
│   └── command_handlers/
└── libraries/

对你的启示:目录结构不用自己发明,抄这套就行。

2025 年 IEEE 研究:Hexagonal 降低 35% 耦合

2025 年 IEEE Software 发表的研究指出:Hexagonal 架构比传统分层架构降低 35% 耦合,维护成本降低 35%。学习曲线 2-4 周。

对你的现实意义:投入 2-4 周把 R·Agent 重构成 Hexagonal,换来后续 35% 的维护成本节省。ROI 很好。

Netflix、Uber 的 ML 系统实践

Netflix 和 Uber 的 ML 系统都用了类似 Hexagonal 的架构。Uber 的 Michelangelo 平台用 “Engine → Adapter” 的隔离方式,把 XGBoost、TensorFlow、PyTorch 等训练框架都隔离成 adapter,模型核心逻辑完全不知道底层框架。

对你的启示:LLM 领域跟 ML 领域是同类问题 —— 都要”业务逻辑不依赖具体引擎”。

Neal Ford 的《Building Evolutionary Architectures》

Neal Ford 提出 Fitness Function 概念,主张”让架构能自动演进,同时自动防止退化”。import-linter 就是这种思想的直接体现。

2025 年的趋势是 AI 辅助架构维护 —— 有研究尝试用 LLM 监控架构演进,但最稳定的还是硬性 fitness function(CI 拦住就是拦住,LLM 判断还有不确定性)。

有争议的:Hexagonal 对小项目是不是过度?

业界有一派声音:小项目用 Hexagonal 是过度工程。

论点:早期项目应该”先跑起来”再说,过早抽象 port/adapter 会让代码膨胀 20%,拖慢开发速度。

反驳(也是本章的立场):

  1. R·Agent 不是小项目 —— 你有 Lefa + Refa + 多种 adapter 的复杂度
  2. 只对”外部依赖”做 Hexagonal,内部逻辑不强求 —— 成本只有 10%,不是 20%
  3. AI 写代码时代,守架构的成本变低了(AI 能帮你写 port/adapter 样板代码),但被 AI 侵蚀架构的风险变高了 —— Hexagonal 的 ROI 比 2020 年更高

对你的决策:R·Agent 做 Hexagonal 是值的。但小项目不用强上。

3.8 学会检验 · 你能讲出来吗?

自检 1 · 用 30 秒解释 Hexagonal 的核心思想

参考答案:“把应用分成三层:domain(业务核心,纯)、adapter(外部适配,脏)、app(编排组装)。依赖方向永远向内指向 domain,domain 不依赖任何外部。这让业务核心能脱离真实环境测试,换 LLM / 换数据库只改 adapter 不改业务。”

自检 2 · 你 R·Agent 里 LLM 调用应该放哪层?为什么?

参考答案:“分两个位置:

  • Port(接口) LLMClient 在 domain/ports/ —— 这是’我们需要一个能生成文本的能力’这个抽象需求
  • Adapter(实现) ClaudeAdapter 在 adapters/llm/ —— 这是’怎么用 Claude SDK 实现这个需求’这个具体技术

domain 里的 SectionAnalyzer 只 import LLMClient port,不 import ClaudeAdapter。具体用哪个 adapter 在 app 层通过依赖注入决定。”

自检 3 · 为什么”业务规则不能漏到 adapter 里”?

参考答案:“因为 adapter 的职责是翻译外部系统的语言,不是做业务判断。如果业务规则(比如 confidence 阈值)漏到 adapter 里,会有三个问题:

  1. 换 adapter 时会丢规则 —— 写新 adapter 忘了加那个 if
  2. 规则不唯一 —— 改阈值时可能漏掉 adapter 里的
  3. 测试变困难 —— 业务测试要 mock adapter,adapter 测试要关心业务

正确做法是 adapter 只负责’把 Claude 的响应 parse 成 dict’,业务判断回到 domain 的 service 层做。”

自检 4 · import-linter 抓到 src.domain.services imports src.adapters.llm.claude,怎么修?

参考答案:“这是典型的依赖反转违规。修复步骤:

  1. 在 src/domain/ports/ 定义 LLMClient 抽象接口(用 Protocol)
  2. src.adapters.llm.claude 的 ClaudeAdapter 保持不变(它在 adapter 层,可以依赖外部库)
  3. 把 src.domain.services.section_analyzer 里的 import ClaudeAdapter 改成 import LLMClient
  4. 构造函数改成 def __init__(self, llm: LLMClient):,接受注入的 adapter
  5. 在 app/config.py 的 build 函数里,把 ClaudeAdapter() 实例传给 SectionAnalyzer

修完再跑 import-linter,绿灯。”

自检 5 · Lefa 和 Refa 怎么共享代码又各自独立?

参考答案:“共享的放 domain,特有的放 app。

  • 两个工作流都用的 SectionAnalyzer、TableProcessor、BusinessRules → 放 domain/
  • Lefa 特有的编排流程(先 parse 再分析再组合)→ app/lefa.py
  • Refa 特有的编排流程(不同的顺序 / 不同的 Stage)→ app/refa.py
  • 两个工作流都 import domain 层的服务,组合成自己的流程
  • domain 层从来不知道 Lefa 和 Refa 的存在,只提供’通用能力’”

自检 6 · 跟一个架构师聊 R·Agent 架构

参考答案(模拟对话):

架构师:“你们 R·Agent 架构怎么分层?”

你:“Hexagonal。三层:domain 是业务核心(纯 Python,无外部依赖),adapters 是外部系统的 adapter 层(LLM、docx 解析、存储),app 是编排层(Lefa、Refa、CLI 入口)。依赖方向向内,domain 不依赖任何外部。”

架构师:“业务规则放在哪?”

你:“统一放 domain/rules.py,用 frozen dataclass 表达。可以从 business_rules.yaml 加载,方便业务方改阈值不改代码。”

架构师:“换 LLM 的影响范围?”

你:“只改 adapter。加一个 OpenAIAdapter 实现 LLMClient Protocol,在 config 加一个分支。大概一天。业务逻辑、Lefa 编排、测试代码全部不动。”

架构师:“怎么防止架构退化?”

你:“用 import-linter 做 fitness function,在 CI 里强制检查依赖方向。domain → adapter 的任何 import 都会 fail CI。code review 还会专门检查 adapter 里有没有业务规则漏出来。”

架构师:“Lefa 和 Refa 的关系?”

你:“两者都是 app 层的 entrypoint,共享 domain。Lefa 编排工作流 A,Refa 编排工作流 B,但都用同一套 SectionAnalyzer、TableProcessor、BusinessRules。改 domain 代码自动对两者生效。”

能这样说话 = 你在跟架构师平等对话了。这是本章的终极目标。

第三章 · 测试分层:LLM 项目的可验证性

3.1 痛点切入 · “跑得通”不等于”测过了”

你跟工程师同事之间有过这样的对话吗?

你:这个 anchor verification 功能测过了吗?

他:跑过,能 work。

你:测了什么 case?

他:我试了一份 CER,出来的结果是对的。

你:换成带表格的呢?

他:……我再试试。

这段对话的本质是:“测试”在你们俩心里根本不是同一件事。

对他来说,“测过了” = “我手动跑了一次,看起来对”。对软件工程层面的测试来说,这叫 smoke test —— 冒烟测试,只能证明”没炸”。真正的测试应该回答的问题是:

  • 所有边界条件都考虑了吗?(空文档、超长文档、纯表格文档、中英混排)
  • 六个月后我改了代码,有东西自动告诉我是不是破坏了原来的功能吗?
  • LLM 今天返回了一个罕见结构,我的 fallback 逻辑真的触发了吗?
  • 整个 pipeline 端到端跑,每个阶段的 Q-Gate 真的在把关吗?

没有测试 = 你的代码质量全靠运气 + 记忆力。

再举个 LLM 项目特有的尴尬:

你让 AI 帮你重构 normalize 函数,AI 说:“重构完成,功能不变。”

你怎么知道它真的”功能不变”?只能靠跑几个你记得的 case。但 normalize 有 17 种边界情况,你记得其中 5 种,另外 12 种 AI 有没有改坏,全凭上线后爆炸才知道。

这一章要回答的核心问题:在一个 AI 写大半代码的项目里,你怎么建立一套”AI 改完代码立刻告诉你破没破坏”的安全网?

答案:测试分层。不同类型的测试覆盖不同层面的确定性,组合起来成为你的回归安全网。

3.2 费曼式核心 · 测试的 4 个底层原理

原理一:测试是写给”未来的你”的合同

契约是写给”其他模块”的合同(第二章),测试是写给“未来自己”的合同。

今天你写了一段代码,测试里写:“给它输入 X,应该返回 Y”。这是你在把对代码行为的理解固化下来。

6 个月后,你或 AI 改了这段代码。如果改动不小心破坏了”X → Y”的行为,测试会立刻红灯。

没有测试的代码,本质是”只有作者当时脑子里懂的代码”。一个月后作者自己都忘了为什么那里要那么写。

原理二:测试金字塔 vs 测试奖杯 —— 你不是传统 Web 应用

传统软件工程教的是金字塔模型:底部大量 unit test,中间一些 integration test,顶上极少 e2e test。

     /\
    /E2\          极少
   /---\
  / Int \         一些
 /-------\
/  Unit   \       大量
-----------

这不适合 LLM 项目。为什么?因为 LLM 的行为本质就是非确定性的 —— 同样输入,同一个模型不同时刻可能给不同输出。单元测试能覆盖的”纯函数逻辑”在 LLM 项目里占比低,主要的风险在集成点(prompt + 模型 + 解析)。

现代 LLM 项目更适合奖杯模型(Kent C. Dodds 提出的 Testing Trophy):

    /E2E\           极少(2-3 个核心流程)
   /----\
  / Int  \          **主要投入** (pipeline 各阶段接合)
 /--------\
/   Unit   \        中等(覆盖纯逻辑)
------------
|  Static  |        底座(mypy + ruff,免费拦住一大半 bug)
------------

差别: - 底座是静态检查(mypy + ruff + 契约 —— 你前两章已经装好了) - integration test 是主战场 —— 这是 R·Agent 的 Q-Gate 该落的地方 - unit test 适量就好 —— 只覆盖纯函数(normalize 字符串、校验规则等) - e2e test 少而精 —— 一两个端到端冒烟就够,跑一次很慢

💡 为什么不用金字塔 金字塔假设”底层单元能独立测试”。但 LLM 项目的”单元”往往是一个 prompt,你没法单独测 prompt —— 必须跟模型一起测,那就是集成测试了。所以 LLM 项目的重心天然在中间层。

原理三:“测试” ≠ “评估”,两件事要分开

在 LLM 项目里,这两个词经常混用,但它们是两种不同的质量保障机制:

测试(Testing)

  • 确定性的 pass / fail
  • 快速(秒级)
  • 在 CI 里跑,每次 commit 都跑
  • 回答:“代码有没有被我改坏?”

评估(Evaluation,evals)

  • 分数(0.0 - 1.0),往往不是 binary
  • 慢(涉及 LLM 调用,分钟级)
  • 在数据集上跑,产出报告
  • 回答:“模型 / prompt / 算法效果有没有变好?”

关系:测试是必要条件(不通过就别合并),评估是充分条件(不通过提示你质量下降了,但可能是可接受的权衡)。

R·Agent 里: - 测试:anchor_verify() 输入这个字符串,必须返回 True(代码逻辑) - 评估:在 50 份真实 CER 上,pipeline 的整体 pass-rate 从 82% 掉到 78% 了(质量指标)

💡 实战建议 在你的 tests/ 目录下分开两个子目录:

tests/
├── unit/           # 确定性测试,每次 CI 都跑
├── integration/    # 确定性测试,每次 CI 都跑
└── evals/          # 评估,定期跑(每周或 release 前)

这样 CI 快,评估独立。

原理四:AAA 模式 · 每一个测试都是一个故事

无论是单元、集成还是 e2e,所有测试都应该遵循 AAA 结构:

Arrange(准备) ──► Act(执行) ──► Assert(断言)
  "如果..."           "那么..."         "应该..."

反面例子(混乱的测试):

def test_normalize():
    result = normalize("hello\r\nworld")
    assert result == "hello\nworld"
    result2 = normalize("")
    assert result2 == ""
    s = "a\\nb\nc"
    assert normalize(s) == "a\nb\nc"

AAA 模式重写(清晰,每个测试讲一个故事):

def test_normalize_converts_crlf_to_lf():
    # Arrange
    input_text = "hello\r\nworld"
    # Act
    result = normalize(input_text)
    # Assert
    assert result == "hello\nworld"


def test_normalize_handles_empty_string():
    assert normalize("") == ""


def test_normalize_converts_literal_backslash_n():
    assert normalize("a\\nb\nc") == "a\nb\nc"

测试名本身就是文档。test_normalize_converts_crlf_to_lf 不用看代码就知道测什么。这比 “test_normalize_1 / test_normalize_2” 好十倍。

pytest 基础(最小够用集)

  • 测试文件命名:tests/test_xxx.py,函数名 test_yyy
  • assert 的用法(pytest 的 assert 有魔法,失败会打印详细信息)

  • conftest.py 里放全局 fixture
  • fixture scope:function(默认)/ class / module / session

参数化测试(同一逻辑,多组数据)

  • 配合 AAA 模式,一次写多个 case

Mock / Stub · 模拟外部依赖

  • unittest.mock.patch 临时替换对象
  • pytest-mock 的 mocker fixture
  • 什么时候该 mock,什么时候不该 mock(这是关键判断)

LLM 项目专属

  • 评估测试:真实跑 LLM,在数据集上算指标(跑得慢,不放在 CI 每次跑)

动作 2:写第一批 unit test(纯函数)

R·Agent 里哪些算纯函数?—— 输入确定,输出确定,不依赖外部(LLM、文件、API)。

标准的 unit test 写法:

# tests/unit/test_normalize.py
import pytest
from src.normalize import normalize, calculate_change_ratio


class TestNormalize:
    """归一化函数测试"""

    def test_crlf_to_lf(self):
        assert normalize("hello\r\nworld") == "hello\nworld"

    def test_literal_backslash_n(self):
        assert normalize("a\\nb") == "a\nb"

    def test_empty_string(self):
        assert normalize("") == ""

    def test_no_change_needed(self):
        assert normalize("hello world") == "hello world"

    def test_mixed_line_endings(self):
        assert normalize("a\r\nb\nc\rd") == "a\nb\nc\nd"

    # 参数化:一次写多个 case
    @pytest.mark.parametrize("input,expected", [
        ("", ""),
        ("a", "a"),
        ("\n", "\n"),
        ("\r\n", "\n"),
        ("\\n", "\n"),
        ("mixed\r\nstuff\\nhere", "mixed\nstuff\nhere"),
    ])
    def test_parametrized(self, input, expected):
        assert normalize(input) == expected


class TestChangeRatio:
    """字符变化比例测试"""

    def test_no_change(self):
        assert calculate_change_ratio("abc", "abc") == 0.0

    def test_completely_different(self):
        ratio = calculate_change_ratio("abc", "xyz")
        assert ratio == 1.0

    def test_partial_change(self):
        ratio = calculate_change_ratio("hello world", "hello WORLD")
        assert 0 < ratio < 0.5

    def test_empty_input(self):
        # 边界:空输入应该返回 0 还是 raise?
        # 这个测试本身就是在"固化你的设计决策"
        assert calculate_change_ratio("", "") == 0.0

import pytest
from src.pipeline import run_normalize_stage

@pytest.mark.integration
class TestL0ToL1:
    """测试 L0 原始输出 → L1 归一化阶段"""

    def test_normalized_output_preserves_call_id(self, sample_raw_llm_output):
        # Arrange
        raw = sample_raw_llm_output
        
        # Act
        normalized = run_normalize_stage(raw)
        
        # Assert - 契约必须保持可追溯
        assert normalized["source_call_id"] == raw["call_id"]

    def test_change_ratio_within_threshold(self, sample_raw_llm_output):
        """Q-Gate: 归一化的改动必须 < 5%"""
        normalized = run_normalize_stage(sample_raw_llm_output)
        assert normalized["change_ratio"] < 0.05

    def test_crlf_normalized(self, sample_raw_llm_output):
        normalized = run_normalize_stage(sample_raw_llm_output)
        assert "\r\n" not in normalized["normalized_text"]
        assert "\n" in normalized["normalized_text"]

    def test_empty_raw_text_handled(self):
        """边界:空输入应当优雅降级,不崩溃"""
        empty_raw = {
            "raw_text": "",
            "model": "test",
            "call_id": "empty",
            "timestamp": "2026-04-19T10:00:00Z",
        }
        normalized = run_normalize_stage(empty_raw)

测试 Q-Gate 触发行为:

# tests/integration/test_q_gates.py
import pytest
from src.pipeline import run_pipeline

class TestL2Fallback:
    """验证 L2 fallback 在 anchor 校验失败时真的触发"""

    def test_anchor_mismatch_triggers_l2_sidecar(self, monkeypatch):
        """当 LLM 悄悄改了原文,必须走 L2 sidecar"""
        # Arrange - mock 一个会篡改原文的 LLM
        def fake_llm_call(prompt):
            return '{"marked_text": "MODIFIED", "markers": []}'
        
        monkeypatch.setattr("src.llm.call_llm", fake_llm_call)
        
        # Act
        result = run_pipeline(original_text="ORIGINAL CONTENT")
        
        # Assert - 降级路径被触发
        assert result["degradation_level"] == "L2"
        assert result["final_text"] == "ORIGINAL CONTENT"  # 保留原文
        assert result["warnings"]  # 告警被记录

这是 R·Agent 里最重要的测试 —— 它把你的”三级降级”机制变成了可验证的行为。

动作 4:mock 掉 LLM(让测试不花钱不慢)

在 integration test 里你不能真调 LLM —— 慢、贵、不稳定。必须 mock。

用 pytest-mock 的 mocker fixture:

# tests/integration/test_llm_error_handling.py
import pytest
from pydantic import ValidationError
from src.pipeline import analyze_section

class TestLLMErrorHandling:
    def test_malformed_llm_response_triggers_fallback(self, mocker):
        """LLM 返回坏 JSON,系统应当 fallback 而非崩溃"""
        # Arrange - mock LLM 返回坏数据
        mocker.patch(
            "src.llm.call_llm",
            return_value='{"broken": json without quotes'
        )
        
        # Act
        result = analyze_section("test input")
        
        # Assert
        assert result["status"] == "fallback"
        assert "malformed_llm_response" in result["errors"]

    def test_llm_missing_required_field(self, mocker):
        """LLM 返回少字段,Pydantic 应当拒绝"""
        mocker.patch(
            "src.llm.call_llm",
            return_value='{"section_id": "sec-01"}'  # 缺了 confidence
        )
        
        with pytest.raises(ValidationError) as exc_info:
            analyze_section("test")
        
        assert "confidence" in str(exc_info.value)

💡 mock 的三条纪律 1. 只 mock 外部依赖(LLM API、数据库、HTTP 调用、文件系统)。不要 mock 你自己写的函数 —— 那样测试在测谎话 2. mock 的对象要尽量接近真实(返回真实结构的数据,不是 Mock()) 3. mock 的位置要在”被使用的地方”而不是”定义的地方”(这是经典坑)

这是跟”测试”严格区分的另一件事。用于回答”模型/prompt 改了之后质量变好还是变差”。

    path = Path(__file__).parent / "datasets/cer_samples.json"
    return json.loads(path.read_text())

@pytest.mark.eval
class TestPipelineQuality:
    """在真实样本集上跑,产出质量报告"""

    def test_overall_pass_rate(self, cer_dataset):
        """pipeline 整体通过率必须 ≥ 80%"""
        results = []
        for sample in cer_dataset:
            result = run_pipeline(sample["input"])
            results.append(result["status"] == "success")
        
        pass_rate = sum(results) / len(results)
        assert pass_rate >= 0.80, f"Pass rate {pass_rate:.2%} below threshold"

    def test_anchor_preservation_rate(self, cer_dataset):
        """原文保真率必须 ≥ 95%"""
        preserved = 0
        for sample in cer_dataset:
            result = run_pipeline(sample["input"])
            if result["final_text"] == sample["input"]:
                preserved += 1
        rate = preserved / len(cer_dataset)
        assert rate >= 0.95

动作 6:测试覆盖率(不追求 100%)

# 安装
pip install pytest-cov

# 跑
pytest --cov=src --cov-report=html --cov-report=term

# 输出

# Name                      Stmts   Miss  Cover
# src/normalize.py            45      2    96%
# src/pipeline.py            120     25    79%
# src/llm.py                  80     35    56%

怎么看: - src/normalize.py 96% ✅ 纯逻辑,覆盖率应该高 - src/pipeline.py 79% ✅ 集成逻辑,80% 左右合理 - src/llm.py 56% ⚠️ LLM 调用,部分路径只能真跑才能覆盖,这个数字可以接受

不追求 100% 的原因: 1. 测试 getter / setter 这种琐碎代码浪费时间 2. 一些 error branch 只在极端场景触发,强测反而让测试变脆 3. LLM 相关代码有些路径只有真调 API 才走到,mock 不了的就接受低覆盖

合理目标: - 核心业务逻辑 ≥ 80% - 整体项目 ≥ 70% - 不要强求 100%

在 pyproject.toml 里设个下限:

[tool.coverage.report]
fail_under = 70

CI 里覆盖率跌破 70% 直接挂,防止慢慢退化。

🔴 3.5.8 救命:flaky test(时好时坏的测试)

症状:同一个测试,跑 10 次有 2 次失败,8 次通过。

常见原因:

  1. 依赖时间(datetime.now() 没 mock)
  2. 依赖顺序(用了会变的 dict 顺序、set)
  3. 依赖外部服务(网络、LLM)没 mock
  4. 竞态条件(多线程、异步)
  5. fixture 状态泄漏(scope 太大,上个测试污染了这个)

定位方法:

# 重复跑 10 次,定位不稳定
pytest tests/flaky_test.py --count=10
# (需要 pytest-repeat 插件)

# 随机打乱顺序跑(暴露顺序依赖)
pytest -p random_order

应对原则:

  • flaky test 比失败的测试更糟 —— 因为团队会开始忽略它
  • 要么修要么删,不要留着”偶尔挂一下没关系”的测试
  • 修不了的,先 @pytest.mark.skip(reason="flaky, see #142"),加 issue

3.6 行业权威怎么做

Martin Fowler 的测试金字塔(原始版本)

Martin Fowler 的经典文章 “TestPyramid”(2012)定义了金字塔模型 —— 底部大量 unit,中间 integration,顶上少量 e2e。这仍然是传统 Web / 企业应用的标准做法。

Kent C. Dodds 的测试奖杯(现代版本)

Kent C. Dodds(Testing Library 作者)在 2018 年提出 Testing Trophy 模型,核心论点:

“Write tests. Not too many. Mostly integration.”

翻译:别写太多测试。大部分写 integration。

他的论据:现代应用有大量”胶水代码”(调用 API、处理状态),unit test 覆盖不到这些胶水;integration test 用较少的测试覆盖更多真实场景;static 检查(TypeScript / mypy)在底座免费拦住一半 bug。

对 LLM 项目尤其适用 —— LLM 项目的”胶水”特别多。

LLM 测试领域的新范式(2025)

DeepEval、LangSmith、Langfuse 这些框架的出现,定义了 LLM 测试的新模式:

“Evaluating LLMs to us is more about choosing the right LLMs through benchmarks, whereas LLM testing is more about exploring the unexpected things that can go wrong in different scenarios.”

翻译:评估是选模型,测试是探索可能出错的场景。两者分开。

主流做法:

  • 传统 pytest 测代码逻辑(确定性)
  • DeepEval / 自制 evals 测 LLM 输出质量(概率性)
  • LLM-as-judge 给输出打分
  • 结果存到 Langfuse / LangSmith,看趋势

LangChain 团队的实践:避免过度 mock

Lincoln Loop 和 LangChain 有一派观点:不要过度 mock LLM。

他们的做法是用 FakeChatModel —— 一个行为像 LLM 但不真调 API的假模型,你提前 push 返回值进去:

fake_model = FakeChatListModel(responses=["42"])
response = chain.invoke({"input": "what's the meaning?"})
assert response == "42"

优势:比 mocker.patch 更接近真实,兼容 LangChain 的完整调用链路,但依然不花钱不慢。

对你的启示:mock 有两种风格 —— 粗暴替换(快)vs 行为模拟(接近真实)。用哪种看场景。

Pytest 官方推荐:AAA + fixture 优先

pytest-with-eric.com(一个被业界引用最多的 pytest 最佳实践站)的建议:

  • AAA 模式是所有测试的基准结构
  • fixture 优先于 setUp/tearDown(pytest 比 unittest 更现代)
  • 每个测试独立,不依赖其他测试的执行顺序
  • 测试名即文档,“test_what_happens_when_xxx”

3.8 学会检验 · 你能讲出来吗?

自检 1:为什么 LLM 项目应该用测试奖杯而不是测试金字塔?

参考答案:“金字塔假设大部分 bug 出在’可独立测试的单元逻辑’里。LLM 项目的 bug 主要出在’胶水层’ —— prompt 构造、response 解析、fallback 触发、契约校验,这些天然是集成测试。另外 LLM 本身非确定性,单元粒度无法隔离测试。所以奖杯把重心放在 integration,是更契合 LLM 项目特性的做法。”

自检 2:“测试”和”评估”的差别是什么?为什么要分开?

参考答案:“测试是确定性的 pass/fail,快,在 CI 每次跑,回答’代码有没有被改坏’。评估是概率性分数,慢,定期跑,回答’质量指标是否退化’。分开的原因:如果混在一起,CI 会变慢且贵,而且评估的’分数下降 2%’不等于 fail,强行 CI 化会导致误报频繁,团队会开始忽略 CI。”

自检 3:什么时候该 mock LLM,什么时候不该?

参考答案:“CI 里的 integration test 必须 mock(否则又慢又贵又不稳定)。evals / 在真实数据集上的质量测试不 mock(mock 了就不是评估了)。mock 的选择:粗暴替换用 mocker.patch,行为模拟用 FakeChatModel 这类。关键纪律:只 mock 外部依赖,不 mock 自己的函数。”

自检 4:R·Agent 的三级降级机制,你会怎么测?

参考答案:“每一级降级都要有专门的集成测试。

L1 正常:mock LLM 返回合格响应 + anchor 校验通过,验证走正常路径。

L2 sidecar:mock LLM 返回合格响应,但人为制造 anchor mismatch,验证 sidecar fallback 触发,final_text 等于原文。

L3 revert:mock LLM 返回彻底坏掉的 JSON,验证系统捕获异常,走 full revert,final_text 等于原文,warnings 记录完整。

每一级都断言 degradation_level 字段,这样改了代码破坏了某一级都会立刻被拦住。”

自检 5:测试覆盖率应该追求多少?为什么不追求 100%?

参考答案:“核心业务逻辑 ≥80%,整体 ≥70%。不追求 100% 的原因:(1) 追求 100% 会写大量测试琐碎代码(getter/setter)的测试,浪费时间;(2) 一些错误分支只在极端场景触发,强测反而让测试变脆;(3) LLM 相关代码的某些路径只能真调才能覆盖。合理目标 + CI 里设 fail_under 防退化,比追求 100% 有用得多。”

自检 6:能跟架构师聊”你们测试策略长什么样”吗?

参考答案(模拟对话):

架构师:“你们 R·Agent 的测试怎么组织的?”

你:“用 Testing Trophy,重心在 integration。底座是 mypy + ruff + Pydantic 契约,第二章我们已经讲过。unit test 只测纯逻辑部分比如 normalize 和 anchor_verify。integration 是主战场,测 pipeline 各阶段契约和 Q-Gate 降级行为。e2e 只有一两个跑完整流程。mock 用 pytest-mock,针对 LLM 和文件系统这类外部依赖。evals 独立目录,不在 CI 跑,每周看 pass rate 趋势。”

架构师:“LLM 怎么测?mock 吗?”

你:“分层处理 —— CI 里的 integration test 全 mock,确保快和稳定。evals 在真实数据集上跑,用自制断言 + DeepEval 辅助,看整体质量趋势。关键是’测试’和’评估’严格分开,不混在同一个 CI job 里。”

能这样对话 = 你真的会了。

5.1 痛点切入 · “看不见”比”做错了”更可怕

你已经做了第 2 章(中间态物化)和第 3 章(Hexagonal)。开发时能看到每个 Stage 的产出,架构上切得清清楚楚。

但这些都是你主动去看才能看到的东西。

线上跑的时候呢?

场景一:业务同事下午四点冲进来

“你们这个东西,昨天我让它跑了一个 CER,怎么结果跟上周跑另一个完全类似的文档不一样?”

你打开代码看,没任何报错。artifacts/ 目录里——昨天那次已经被今天的新任务覆盖了。或者虽然还在,但你不知道是哪一次运行产出的(你的 ArtifactStore 按时间戳命名,找对时间戳要搜日志)。

你只能说”让我查一下”,然后花两小时拼凑昨天到底发生了什么。

场景二:R·Agent 悄悄变慢

你没注意到,但过去两周,L2 的平均延迟从 2.3 秒涨到了 6.8 秒。到今天业务方说”这东西现在怎么这么慢”,你才开始查。查了半天,原因是某次 prompt 改动让 Claude 输出更长了,token 消耗也上涨了 40%。

这个退化本该早两周就被发现。但你没有看趋势的机制,只能被动等用户抱怨。

场景三:L2 fallback 悄悄在用

你做了 L2/L3 分层(第 2 章)。L2 原生输出偶尔会触发 fallback 回到上一版 prompt。这个 fallback 机制本来是”保底”,不该经常用。

你不知道它到底多久触发一次。可能过去一个月被触发了 800 次 —— 意味着你的新 prompt 正在被”保底”兜着,实际上效果比你以为的差一大截,但你看不到。

三个场景的共同点

  • 链路不可追溯:哪一次运行干了什么,事后拼不回来
  • 趋势不可见:慢慢退化看不到,出事了才知道
  • 关键事件不发声:fallback、降级、契约违规静默发生

这就是没有可观测性的代价 —— 出问题永远是”事后追着查”,永远被动。

读完这一章,你能做到:

  • ✅ 任何一次线上运行,你都能在 5 分钟内找回它的完整链路(每个 Stage 的输入输出、耗时、LLM token、L3 规则触发)
  • ✅ 关键退化在影响业务之前就告警(延迟、fallback 率、契约违规率)

  • ✅ 跟架构师说”我们有完整的 trace-log-metric 闭环”不脸红

5.2 费曼式核心 · 可观测性的 3 个底层原理

原理一:三件套各司其职

现代可观测性有一套标准模型,叫 三件套(Three Pillars of Observability):

件 回答什么问题 特点 你的 R·Agent 场景
Log(日志) “发生了什么?” 离散事件,带上下文 LLM 调用完成、fallback 触发、错误发生
Metric(指标) “趋势怎样?” 数值聚合,按时间走 L2 平均延迟、fallback 率、token 消耗
Trace(链路) “这次执行经过了哪些环节?” 把一次完整执行串起来 一次 Lefa 运行从 Stage 0 到 Stage 5

三件套的核心是”各回答一种问题”,不要混用:

  • 想查一个具体事件(昨天下午三点那次挂了)→ Log
  • 想看系统整体健康(最近一周表现咋样)→ Metric
  • 想追一次请求的完整路径(这次运行 Stage 3 为什么走了 fallback)→ Trace

反模式:用 log 当 metric 用 —— “我每次 LLM 调用都打一行 log 写延迟,然后 grep 统计平均值”。可以做,但扩展性差。过 1000 条 log 以上就力不从心。Metric 专门为此设计。

💡 术语小词典 · Three Pillars of Observability

这三件套不是某个公司发明的,是 Honeycomb、Datadog、Grafana 这些可观测性厂商共同推广的标准模型。2020 年前后成为业界共识。

有人会说”四件套,还要 Event”—— 但 Event 本质上是 Log 的一个子类(高重要性、带语义的 log),不单独列出来也行。

原理二:trace_id 是可观测性的身份证

这条原理决定了你能不能”把一次运行拼回来”。

想象一次 Lefa 运行,走过 Stage 0 到 Stage 5,每个 Stage 调用了 Skill 函数,每个 Skill 函数可能又调了 LLM。这些环节打出了 100 条日志。

没有 trace_id 时:

10:05:12 [INFO] parsing PDF
10:05:15 [INFO] calling LLM
10:05:18 [INFO] parsing PDF
10:05:20 [INFO] calling LLM
10:05:22 [ERROR] section_id missing
...

哪两条 log 属于同一次运行?不知道。 你昨天跑了 3 次 Lefa,log 混在一起,永远拼不回来。

有 trace_id 时:

10:05:12 [INFO] parsing PDF        trace_id=abc123
10:05:15 [INFO] calling LLM        trace_id=abc123
10:05:18 [INFO] parsing PDF        trace_id=def456   ← 另一次运行
10:05:20 [INFO] calling LLM        trace_id=abc123
10:05:22 [ERROR] section_id missing trace_id=abc123
...

用 grep "trace_id=abc123" 就能把一次运行的所有日志拉出来。

trace_id 的铁律:

  1. 一次运行开始时生成一个 UUID,贯穿整个运行
  2. 每条日志必须带 trace_id
  3. 跨函数、跨模块调用时 trace_id 不能丢 —— Python 里用 contextvars 自动贯穿

💡 术语小词典 · trace_id vs span_id vs correlation_id

  • trace_id:一次完整运行的 ID(跑一次 Lefa = 一个 trace_id)
  • span_id:这次运行中某个环节的 ID(Stage 2 是一个 span,Stage 3 是另一个)
  • correlation_id:请求级别的 ID,通常等于 trace_id,web 领域用得多

对你 R·Agent 当前规模:只用 trace_id 就够。span_id 是 OpenTelemetry 级别的东西,真做微服务时再说。

原理三:指标要分三层 —— 业务 / 系统 / 基础设施

做指标的人常见的错误是”什么都打”,结果看板上 200 个指标,没人看。

正确的分层:

第一层 · 业务指标(Business Metrics) ← 最重要

回答”R·Agent 对业务的价值指标”: - 整体 pass rate(pipeline 完成且通过 Q-Gate 的比例) - 一次运行平均耗时(端到端体验) - 人工复核触发率(多少份文档需要人工看)

第二层 · 系统指标(System Metrics)

回答”R·Agent 内部健康”: - 每个 Stage 的耗时分布 - L3 规则触发率(哪条规则正在被打补丁) - fallback 触发率(L2 / L3 降级多频繁) - LLM 调用 token 消耗

第三层 · 基础设施指标(Infrastructure Metrics)

回答”服务器 / 网络健康”: - CPU / 内存 - 磁盘空间(artifacts 目录爆了吗) - API 延迟

对 R·Agent 当前规模:先做第一层和第二层,第三层等你真的部署到服务器了再说。

💡 术语小词典 · 黄金信号 vs USE vs RED

关于”该监控什么”有三套主流方法论: - 黄金信号(Google SRE):Latency / Traffic / Errors / Saturation - USE(Brendan Gregg):Utilization / Saturation / Errors - RED(Tom Wilkie):Rate / Errors / Duration

对你 R·Agent 来说,RED 最适用 —— 每个 Stage 的 rate(调用次数)、errors(失败次数)、duration(耗时)三件事打出来,80% 的问题都能看到。

动作 1:最小 structlog 配置

# src/observability/logging_config.py
import logging
import structlog
from structlog.contextvars import merge_contextvars

def configure_logging(env: str = "production"):
    """给整个应用配置结构化日志。在应用启动时调用一次。"""
    
    # 基础 processor 链
    shared_processors = [
        merge_contextvars,                      # 自动带入 contextvar(trace_id 等)
        structlog.stdlib.add_log_level,         # 加 level 字段
        structlog.stdlib.add_logger_name,       # 加 logger 名
        structlog.processors.TimeStamper(fmt="iso", utc=True),
        structlog.processors.StackInfoRenderer(),
        structlog.processors.format_exc_info,   # 异常的完整 stack trace
    ]
    
    if env == "production":
        # 生产:JSON 输出给日志聚合系统
        processors = shared_processors + [
            structlog.processors.JSONRenderer(ensure_ascii=False),
        ]
    else:
        # 开发:人可读的带颜色输出
        processors = shared_processors + [
            structlog.dev.ConsoleRenderer(colors=True),
        ]
    
    structlog.configure(
        processors=processors,
        wrapper_class=structlog.stdlib.BoundLogger,
        logger_factory=structlog.stdlib.LoggerFactory(),
        cache_logger_on_first_use=True,
    )
    
    # 让标准 logging 也用 structlog 处理(防止第三方库的 log 不一致)
    logging.basicConfig(format="%(message)s", level=logging.INFO)

动作 2:用 contextvars 让 trace_id 自动贯穿

这是整个章节最关键的一个技巧。学会它,你 R·Agent 的所有代码都能自动带上 trace_id,不用手动传。

# src/observability/tracing.py
import uuid
import structlog
from structlog.contextvars import bind_contextvars, clear_contextvars

log = structlog.get_logger()


def start_trace(run_name: str = "lefa") -> str:
    """开始一次运行,返回 trace_id。"""
    trace_id = f"{run_name}_{uuid.uuid4().hex[:12]}"
    clear_contextvars()  # 清除上一次的
    bind_contextvars(trace_id=trace_id, run_name=run_name)
    log.info("trace.started", trace_id=trace_id)
    return trace_id


def end_trace(status: str = "success"):
    """结束一次运行。"""
    log.info("trace.ended", status=status)
    clear_contextvars()

在 Lefa 里这样用:

# src/app/lefa.py
from src.observability.tracing import start_trace, end_trace

def run_lefa(input_pdf: str):
    trace_id = start_trace("lefa")
    try:
        # 所有后续的 log 自动带 trace_id
        stage0_output = run_stage0(input_pdf)
        stage1_output = run_stage1(stage0_output)
        # ...
        end_trace("success")
    except Exception:
        end_trace("failed")
        raise

💡 为什么 contextvars 比全局变量好

Python 的全局变量(模块级 trace_id = ...)在多线程 / asyncio 下会互相污染 —— 两个并发跑的 Lefa 会抢同一个全局 trace_id。contextvars 天然是”任务局部”的,每个任务/线程有自己独立的一份。这就是为什么 Python 3.7+ 专门引入这个机制。

动作 3:给每个 Stage 加”边界日志”

原则:Stage 进入时打一条 log,退出时打一条,只打边界,不打每一步(否则 log 太噪)。

# src/domain/services/stage_base.py
import time
import structlog
from contextlib import contextmanager

log = structlog.get_logger()


@contextmanager
def stage_context(stage_name: str, **metadata):
    """Stage 执行的上下文管理器。
    
    用法:
        with stage_context("stage2", input_size=100) as ctx:
            result = do_work()
            ctx["output_size"] = len(result)
    """
    start = time.monotonic()
    log.info(f"{stage_name}.started", **metadata)
    ctx = dict(metadata)
    try:
        yield ctx
        duration_ms = (time.monotonic() - start) * 1000
        log.info(
            f"{stage_name}.completed",
            duration_ms=round(duration_ms, 2),
            **ctx
        )
    except Exception as e:
        duration_ms = (time.monotonic() - start) * 1000
        log.error(
            f"{stage_name}.failed",
            duration_ms=round(duration_ms, 2),
            error=str(e),
            error_type=type(e).__name__,
            exc_info=True,
            **ctx
        )
        raise

Stage 里用:

        ctx["markers_count"] = len(result.get("markers", []))

动作 4:关键事件单独打 “event log”

某些事件必须引起注意,应该用专门的 event name,方便告警和查询:

# 降级事件

            stage="stage2",
            reason="anchor_mismatch",
            original_confidence=0.3)

log.error("degradation.l3_revert_triggered",
          stage="stage3", 
          reason="malformed_llm_output")

# 契约违规事件
log.error("contract.schema_violation",
          schema="Stage2FinalOutput",
          field="confidence",
          expected="float",
          got="str")

# Q-Gate 失败事件
log.warning("qgate.failed",
            gate="stage2_confidence",
            field="confidence",
            value=0.45,
            threshold=0.6)

为什么要用专门的 event name:

  1. 便于告警:告警规则可以直接匹配 event="degradation.l2_fallback_triggered",不用 grep 模糊匹配
  2. 便于统计:可以直接 jq | group_by(.event) | count 看各种事件频率
  3. 便于跨团队沟通:degradation.l2_fallback_triggered 这个名字本身就是一个 API

命名约定:domain.action 格式,用 . 分层: - stage0.started / stage0.completed / stage0.failed - postprocess.rule_triggered - degradation.l2_fallback_triggered - contract.schema_violation - qgate.passed / qgate.failed - llm.call_started / llm.call_completed / llm.call_failed

# scripts/compute_metrics.py
import subprocess
import json
from pathlib import Path
from datetime import datetime


def compute_daily_metrics(log_file: Path) -> dict:
    def jq(query: str) -> list:
        result = subprocess.run(
            ["jq", "-s", query, str(log_file)],
            capture_output=True, text=True
        )
        return json.loads(result.stdout or "[]")
    
    total_runs = jq('map(select(.event == "trace.started")) | length')
    l2_fallbacks = jq('map(select(.event == "degradation.l2_fallback_triggered")) | length')
    l3_reverts = jq('map(select(.event == "degradation.l3_revert_triggered")) | length')
    stage_timings = jq('''
        map(select(.event | endswith(".completed"))) |
        group_by(.event) |
        map({
            stage: .[0].event,
            avg_ms: ([.[].duration_ms] | add / length),
            count: length
        })
    ''')
    
    return {
        "date": datetime.now().strftime("%Y-%m-%d"),
        "total_runs": total_runs,
        "l2_fallback_rate": l2_fallbacks / total_runs if total_runs else 0,
        "l3_revert_rate": l3_reverts / total_runs if total_runs else 0,
        "stage_timings": stage_timings,
    }


if __name__ == "__main__":
    metrics = compute_daily_metrics(Path("logs/app.log"))
    history_dir = Path("metrics/history")
    history_dir.mkdir(parents=True, exist_ok=True)
    out = history_dir / f"{metrics['date']}.json"
    out.write_text(json.dumps(metrics, indent=2))

# scripts/check_alerts.py
import json
from pathlib import Path
from datetime import datetime, timedelta


ALERT_RULES = [
    {
        "name": "l2_fallback_rate_too_high",
        "description": "L2 fallback 率超过 20%",
        "check": lambda m: m.get("l2_fallback_rate", 0) > 0.20,
        "severity": "warning",
    },
    {
        "name": "l3_revert_spike",
        "description": "L3 revert 率比一周前上升 2 倍以上",
        "check": lambda m, m_week_ago: (
            m.get("l3_revert_rate", 0) > 0.05 and
            m_week_ago.get("l3_revert_rate", 0) > 0 and
            m["l3_revert_rate"] / m_week_ago["l3_revert_rate"] > 2.0
        ),
        "severity": "critical",
        "needs_comparison": True,
    },
]


def load_metrics(date: str):
    path = Path(f"metrics/history/{date}.json")
    if not path.exists():
        return None
    return json.loads(path.read_text())


def check_alerts():
    today = datetime.now().strftime("%Y-%m-%d")
    week_ago = (datetime.now() - timedelta(days=7)).strftime("%Y-%m-%d")
    today_metrics = load_metrics(today)
    week_ago_metrics = load_metrics(week_ago) or {}
    
    if not today_metrics:
        return
    
    alerts = []
    for rule in ALERT_RULES:
        if rule.get("needs_comparison"):
            triggered = rule["check"](today_metrics, week_ago_metrics)
        else:
            triggered = rule["check"](today_metrics)
        if triggered:
            alerts.append(rule)
    
    if alerts:
        send_alerts(alerts)

5.5 日常操作手册 · 按场景查

🟢 5.5.1 打 log 到底该用什么 level

业界最常见的误用:WARNING 泛滥。把”正常的降级”打成 WARN,结果告警疲劳,真正的 WARN 被淹没。

严格纪律:

Level 什么时候用 例子
DEBUG 开发排查细节,生产默认不输出 chunk[0] = 'section A'
INFO 正常业务事件,信息性 stage2.completed / trace.started
WARNING 异常但已降级处理 L2 fallback triggered / Q-Gate threshold barely met
ERROR 降级失败,需要人工介入 L3 revert failed / pipeline halted

误区清单:

  • ❌ 把 stage2.completed 打成 WARN(它是正常事件)
  • ❌ 把 L2 fallback 打成 ERROR(它是正常降级,不是错误)
  • ❌ 把解析到一个奇怪字段打成 ERROR(解析成功了,只是警告)
  • ✅ L3 revert failed, pipeline halted → ERROR(真正需要人干预)

口号:WARN 是”有点不对劲”,ERROR 是”该去修”。能区分这两个,告警疲劳就解决了一半。

🟢 5.5.2 怎么找回一次运行的完整链路

前提:所有 log 都有 trace_id,都走 JSON 输出到 logs/app.log。

常用命令:

# 拉一次运行的所有 log
jq 'select(.trace_id == "lefa_abc123def456")' logs/app.log

# 按时间排序
jq 'select(.trace_id == "lefa_abc123def456")' logs/app.log | \
  jq -s 'sort_by(.timestamp)'

# 只看关键事件(start / completed / failed / degradation)
jq 'select(.trace_id == "lefa_abc123def456") | 
    select(.event | test("(started|completed|failed|degradation)"))' logs/app.log

推荐一个小工具:写成一个 bash alias

# 在 .bashrc 里
trace() {
  jq -s --arg tid "$1" '
    map(select(.trace_id == $tid)) | 
    sort_by(.timestamp) |
    map("\(.timestamp) [\(.level)] \(.event) \(.duration_ms // "")")[]
  ' logs/app.log
}

# 用法
trace lefa_abc123def456

🟢 5.5.3 怎么判断 log 打太多还是太少

测试方法:拿一次正常运行,数它产出了多少条 log。

  • < 20 条/次 → 打太少,关键事件可能没覆盖
  • 20-100 条/次 → 合理范围
  • > 500 条/次 → 打太多,生产日志会爆炸

打太多的典型症状: - 每个循环迭代都打一条 log(把 for loop 里的 log 降级到 DEBUG) - 每个 LLM 调用打 5 条 log(合并成 2 条:started / completed)

减少 log 的正确做法: 1. 把循环内 log 降级为 DEBUG(生产不输出) 2. 把多条相关 log 合并成一条(一个事件一条) 3. 用 sampling:比如每 100 次 LLM 调用才打一条 INFO,统计汇总

🟡 5.5.4 log 里应该带哪些上下文?

每条 log 的基础字段(structlog 自动加): - timestamp (ISO 8601 UTC) - level - logger - event - trace_id (通过 contextvars)

建议额外带的业务字段: - stage:当前在哪个 Stage(stage0 / stage1 / …) - input_size:输入规模 - output_size:输出规模 - duration_ms:耗时 - confidence:LLM 置信度 - model:用的哪个 LLM 模型 - run_name:Lefa / Refa / …

不该打进 log 的东西: - ❌ 完整文档内容(太大,log 会爆) - ❌ 用户 API key / 密码 - ❌ 每次调用 LLM 的完整 prompt(存 artifact 就够) - ❌ 完整的 LLM response(同上) - ⚠️ 高基数字段(每次都不一样的 UUID、session ID 等)

🟡 5.5.5 artifact(第 2 章)和 log 怎么配合?

分工原则:

  • Log 记”发生了什么”:事件、耗时、决策 —— 小数据,文本为主
  • Artifact 记”数据长什么样”:每个 Stage 的完整输入输出 —— 大数据,JSON/二进制

两者通过 trace_id 关联:

log.info("stage2.completed", 
         duration_ms=2347,
         artifact_path=f"artifacts/{trace_id}/stage2_l3_fixed.json")

存储策略:

  • Log:保留 7-30 天
  • Artifact:保留 3-7 天
  • 失败 / 告警过的 trace 的 artifact:自动迁移到 artifacts/failed/,不被清理任务删

5.6 行业权威怎么做

Honeycomb 的”Observability 2.0”

Honeycomb 创始人 Charity Majors 2022 年提出 “Observability 2.0” 概念,核心观点:

“传统监控是’我已经知道会出什么问题,所以监控它’;可观测性是’我不知道会出什么问题,所以留下能查任何问题的数据’”。

对你的 R·Agent 的启示:不要只监控你已知的指标,更要让日志 / trace 足够丰富,让未来任何意想不到的问题都能事后重现。

Google SRE 的”黄金信号”

Google SRE 书里提出的监控四件套:Latency / Traffic / Errors / Saturation。

对你 R·Agent 的映射:

黄金信号 R·Agent 对应
Latency 每个 Stage 的 p50/p95 耗时
Traffic 一小时内跑了多少次 Lefa
Errors failed / degradation 事件率
Saturation 磁盘、内存使用率

Tom Wilkie 的 RED 方法

Grafana Labs 的 Tom Wilkie 提出简化版”RED”:Rate / Errors / Duration。

对 R·Agent 当前规模:RED 最实用。每个 Stage 打 Rate(计数)、Errors(失败)、Duration(耗时)三件事,80% 的问题都能看到。

OpenTelemetry · 真需要时再看

OpenTelemetry 是可观测性的现代标准。但它很重,对 R·Agent 当前规模是过度。

什么时候上: - R·Agent 部署到生产服务器 - 有多个服务协作 - 要对接 Datadog / Grafana / Jaeger

2025 年冒出一批专门针对 LLM 的可观测性产品:Langfuse / LangSmith / Helicone。

对你的启示:不急着上。等你真的有 20+ 个 prompt 要管理、要做 A/B 测试时再看。

5.8 学会检验 · 你能讲出来吗?

自检 1 · 三件套各回答什么问题?

参考答案:“Log 回答’发生了什么’——离散事件,带完整上下文,用于事后复盘。Metric 回答’趋势怎样’——数值聚合,按时间查看,用于实时监控和告警。Trace 回答’一次执行经过了哪些环节’——把一次完整运行的所有 span 串起来。三者配合:事前告警(metric),事中定位(trace),事后复盘(log)。”

自检 2 · 为什么必须用 contextvars 而不是全局变量?

参考答案:“Python 的全局变量在多线程 / asyncio 下会互相污染。contextvars 天然是任务局部的,每个任务有自己独立的一份。Python 3.7+ 专门为这个场景引入 contextvars,structlog 原生支持,用 bind_contextvars(trace_id=...) 一次绑定,所有下游代码自动拾取。”

自检 3 · WARN 和 ERROR 的精确界限是什么?

参考答案:“WARN = ‘异常但已降级处理,不需要人立即看’。比如 L2 fallback 触发了 —— 这是设计内的降级。ERROR = ‘降级失败或真正出错,需要人介入’。比如 L3 revert 失败、pipeline halt。纪律:把 WARN 和 ERROR 分清楚,告警疲劳问题就解决一半。”

自检 4 · 你怎么定位昨天下午三点那次运行出了什么问题?

参考答案:“分三步:(1) 从业务方那里拿到触发时间和文件名。(2) 用 jq 按时间窗口找到那次运行的 trace_id。(3) 用 trace_id 拉出所有 log 和 artifacts。”

自检 5 · R·Agent 现在什么时候不用上 Prometheus?

参考答案:“当一天的日志量 < 1GB、Stage 数 < 20、不做实时 dashboard 时,用 jq + cron 聚合足够。Prometheus 的价值在大规模 + 实时,对批处理、低频的 R·Agent 是过度。”

自检 6 · 跟一个架构师聊 R·Agent 的可观测性

参考答案:“structlog 结构化日志,contextvar 贯穿 trace_id。每个 Stage 边界打 started/completed/failed 三类事件,关键业务事件用命名空间事件名。每次运行独立 trace_id,事后 jq 一行命令拉完整链路。指标用 jq 聚合 + cron 定时计算,分业务/系统/基础设施三层。告警走 Slack webhook + 邮件。现阶段不上 Prometheus/OpenTelemetry,当前规模过度。”

AI 不读你的 README,也不会看你的 CONTRIBUTING.md。它只看代码上下文。

场景 3 · 你自己累的时候

周五下午,你修一个紧急 bug,改完直接 commit fix bug 推上去。第二个月你看 git log,完全不记得”那个 bug 是修的什么”。规范在你自己疲惫的时候第一个被丢掉。

三个场景的共同点

规范靠自觉的时候,违反规则的成本 = 0(顶多被人嘀咕一下),遵守规则的成本 > 0(要思考、要查、要返工)。

经济学规律告诉你这种系统必然会退化:成本不对称的规则,无法长期维持。

解决方案 · 让违反规则的成本 = 无法合并 PR

CI 的本质 不是”自动跑测试”,是 “把成本不对称翻转过来”。

  • 遵守规则:你的 PR 绿灯,自动合并
  • 违反规则:你的 PR 红灯,你必须修

从这一秒起,违反规则的成本变成了”你的 PR 卡住、你的 feature 不能上线”。这是任何人都不愿意承担的代价。

整本书的所有规范,最终都要塞进 CI。否则它们就是空气。

本章要带你到的终点

读完这一章,你能:

  • ✅ 配出一份最小 GitHub Actions CI(150 行 yaml),覆盖 lint / type / test / 架构 / commit
  • ✅ 本地用 pre-commit 提前拦截,不用等推到远程才发现
  • ✅ 理解每一条 CI 检查在守哪条规范(不是抄配置,是懂为什么)
  • ✅ CI 跑得够快(整套 < 3 分钟),不让团队等到怀疑人生
  • ✅ 会处理 flaky CI,知道什么时候允许临时绕过、什么时候必须修

6.2 费曼式核心 · CI 的 3 个底层原理

原理一:CI 是”门禁”,不是”测试”

很多人误解 CI 是”跑测试的地方”。测试只是 CI 的一种内容。

CI 的真正定位是门禁(gate):

PR 提交
   ↓
CI 门禁(gate)
   ├─ 检查 1:代码风格符合规范吗?
   ├─ 检查 2:类型注解正确吗?
   ├─ 检查 3:测试都过吗?
   ├─ 检查 4:覆盖率达标吗?
   ├─ 检查 5:架构边界没被违反吗?
   ├─ 检查 6:Commit 消息符合规范吗?
   └─ 检查 7:有没有秘钥泄漏?
   ↓
全部通过 → 允许合并
任一失败 → 拒绝合并

把所有想守的规则,都变成 CI 里的一个检查项。规则数量 = 检查项数量。

💡 术语小词典 · CI / CD / CI Gate

  • CI(Continuous Integration):持续集成。代码合并到主干前自动跑各种检查
  • CD(Continuous Delivery / Deployment):持续交付 / 部署。代码合并后自动发布
  • CI Gate(质量门):CI 里的检查项,任一失败就拒绝合并

本章只讲 CI,不讲 CD。CD 涉及部署、生产环境、回滚等,对 R·Agent 当前规模过度。

原理二:本地拦一道,CI 再拦一道,共两道防线

你不会想等推到远程、CI 跑了 3 分钟、然后被告知”你格式错了”。

正确做法:本地 pre-commit hook 先拦一次,CI 再拦一次。

你写代码 ──► git commit ──► pre-commit hook(本地)
                               │
                ┌──────────────┴──────────────┐
                │                             │
            通过 ✅                      失败 ❌
                │                             │
            git push 到远程                改完再 commit
                │
                ▼
            CI gate(远程)
                │
        ┌───────┴───────┐
        │               │
    通过 ✅         失败 ❌
        │               │
    PR 合并          改完再推

为什么要两道:

  • pre-commit hook 快(秒级),但只能拦本地能跑的检查(lint、format、commit 消息)。用户可以 --no-verify 绕过
  • CI 慢(2-3 分钟),但强制(没人能绕过)。能跑更复杂的检查(完整测试、覆盖率、跨文件分析)

铁律:CI 是真相,pre-commit 只是加速反馈。两者检查内容应该一致或重叠,不要冲突。

💡 术语小词典 · pre-commit framework

有一个跨语言的工具就叫 pre-commit(https://pre-commit.com),它是专门管理 git hooks 的框架,不是普通的 git pre-commit hook。

区别: - 原始 git pre-commit hook:你自己写 shell 脚本,每人每个 repo 都要配,容易不一致 - pre-commit 框架:用一个 .pre-commit-config.yaml 声明要跑什么,pre-commit install 一行命令所有人配置一致

原理三:CI 的速度决定团队的纪律

一个常见反模式:CI 跑 15 分钟。

结果:

  • 同事不愿意频繁提 PR(太烦)
  • 大 PR 多了,review 困难
  • 等不及 CI 跑完就先做别的,事后 forget
  • “反正 CI 慢,我先 force push 上去再说”

CI 速度对纪律的影响是非线性的:

CI 时长 体验 团队行为
< 1 分钟 即时反馈 频繁小 PR,每次都看
1-3 分钟 可接受 提 PR 后顺便干点别的
3-10 分钟 烦 攒一波再提,大 PR 多
> 10 分钟 痛苦 开始想各种办法绕过

目标:CI 总时长控制在 3 分钟内。具体怎么做(6.4 动作 6 会讲): - 选 fast 工具(ruff 比 pylint 快 100 倍) - 用 cache(依赖、mypy cache) - 并行 job - 选择性跑(改文档不跑 pytest)

💡 术语小词典 · 反馈循环(Feedback Loop)

软件工程里的核心概念:问题发现得越早,修复成本越低。

  • 写代码时发现错(IDE 红线) → 1 秒,成本极低
  • commit 时发现错(pre-commit) → 5 秒
  • PR 时发现错(CI) → 3 分钟
  • 合并后发现错(线上监控) → 1 小时
  • 用户报告 → 1 天 + 信任损失

CI 的价值是把”用户报告”级别的问题压到”PR 时”级别。

6.4 要会什么 · 6 个核心动作

动作 1:写一份最小可用的 .pre-commit-config.yaml

第一道防线:本地 hook。

# .pre-commit-config.yaml
repos:
  # ----- 基础卫生 -----
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace        # 删行尾空格
      - id: end-of-file-fixer          # 文件末尾保证换行
      - id: check-yaml                 # YAML 语法检查
      - id: check-added-large-files    # 拦大文件
        args: ['--maxkb=500']
      - id: check-merge-conflict       # 拦 merge conflict 残留
      - id: check-json                 # JSON 语法检查

  # ----- 秘钥扫描 -----
  - repo: https://github.com/Yelp/detect-secrets
    rev: v1.5.0
    hooks:
      - id: detect-secrets
        exclude: package-lock.json

  # ----- Python 代码风格 + lint -----
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff           # lint
        args: [--fix]
      - id: ruff-format    # format(替代 black)

  # ----- Commit 消息规范 -----
  - repo: https://github.com/compilerla/conventional-pre-commit
    rev: v3.4.0
    hooks:
      - id: conventional-pre-commit
        stages: [commit-msg]
        args: []

安装并启用:

pip install pre-commit
pre-commit install --hook-type pre-commit --hook-type commit-msg

第一次跑(把整个 repo 整理一遍):

pre-commit run --all-files

第一次会输出大量”自动修复了 X”。让它跑完,然后 git add . && git commit -m "chore: apply pre-commit fixes"。

之后每次 commit:

$ git commit -m "update stuff"

trailing-whitespace.....................................................Passed
end-of-file-fixer.......................................................Passed
ruff....................................................................Passed
ruff-format.............................................................Passed
conventional-pre-commit.................................................Failed
- hook id: conventional-pre-commit
- exit code: 1

Bad commit message: "update stuff"
Expected: <type>(<scope>): <description>
Example: feat(parser): add support for PDF extraction

Commit 被拒。你必须改 commit 消息才能继续。

动作 2:写最小可用的 GitHub Actions CI

第二道防线:远程 CI。

# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

# 同一 PR 后续 push 自动取消之前的运行,省 CI 配额
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  # ===== Job 1: 静态检查(快,几秒)=====
  lint:
    name: Lint & Format
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true
      
      - name: Install dependencies
        run: uv sync --frozen
      
      - name: Run ruff (lint)
        run: uv run ruff check . --output-format=github
      
      - name: Run ruff (format check)
        run: uv run ruff format --check .

  # ===== Job 2: 类型检查 =====
  typecheck:
    name: Type Check
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true
      
      - name: Install dependencies
        run: uv sync --frozen
      
      - name: Run mypy
        run: uv run mypy src/

  # ===== Job 3: 架构边界(Hexagonal)=====
  architecture:
    name: Architecture Boundaries
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true
      
      - name: Install dependencies
        run: uv sync --frozen
      
      - name: Lint imports
        run: uv run lint-imports

  # ===== Job 4: 测试 + 覆盖率 =====
  test:
    name: Tests
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Install uv
        uses: astral-sh/setup-uv@v3
        with:
          enable-cache: true
      
      - name: Install dependencies
        run: uv sync --frozen
      
      - name: Run unit + integration tests
        run: |
          uv run pytest tests/unit tests/integration \
            --cov=src \
            --cov-report=term \
            --cov-report=xml \
            --cov-fail-under=70 \
            -v
      
      - name: Upload coverage
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: coverage-report
          path: coverage.xml

Job 设计:4 个 job 并行跑,总时长约等于最慢的那个 job。

字段解释: - concurrency + cancel-in-progress:同一个 PR 推新 commit,自动取消老的运行(省 CI 时间和钱) - uv 替代 pip install:快 10-100 倍 - --output-format=github:让 ruff 错误显示在 PR 的代码 diff 视图上 - --cov-fail-under=70:覆盖率 < 70% 直接 fail

动作 3:开启 Branch Protection,让 CI 变成强制门禁

没有 branch protection 的 CI = 装饰。任何人都能直接合并红灯的 PR。

配置步骤(以 GitHub 为例):

  1. 进入 repo → Settings → Branches → Add rule
  2. Branch name pattern: main
  3. 勾选:
    • ☑ Require a pull request before merging
    • ☑ Require approvals(至少 1 个 reviewer,小团队就你自己也算)
    • ☑ Require status checks to pass before merging
      • 在搜索框输入并勾选你 4 个 CI job:lint / typecheck / architecture / test
    • ☑ Require branches to be up to date before merging(防止 stale PR 合入)
    • ☑ Do not allow bypassing the above settings(管理员也不能绕)
  4. Save changes

这一步是整本书的”圣经”。没做这一步,前面所有规范都是建议。做了这一步,所有规范都是法律。

动作 4:配合 R·Agent 的具体配置文件

完整的 R·Agent CI 配置不只 .github/workflows/ci.yml,还需要配套的 pyproject.toml:

# pyproject.toml
[project]
name = "ragent"
version = "0.3.0"
requires-python = ">=3.11"

[tool.ruff]
line-length = 100
target-version = "py311"

[tool.ruff.lint]
select = [
    "E",   # pycodestyle errors
    "W",   # pycodestyle warnings
    "F",   # pyflakes
    "I",   # isort (import sorting)
    "N",   # naming conventions
    "B",   # flake8-bugbear (常见 bug)
    "UP",  # pyupgrade (用现代语法)
    "S",   # bandit (安全)
    "RUF", # ruff-specific
]
ignore = [
    "E501",  # line too long(format 会处理)
    "S101",  # assert(测试里要用)
]

[tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S"]  # 测试里允许 assert / mock

[tool.mypy]
python_version = "3.11"
strict = true
disallow_untyped_defs = true
warn_unused_ignores = true
# Hexagonal 重点:domain 必须严格
[[tool.mypy.overrides]]
module = "src.domain.*"
strict = true
disallow_any_explicit = true  # domain 禁止 Any

[tool.pytest.ini_options]
testpaths = ["tests"]
markers = [
    "unit: unit tests (fast)",
    "integration: integration tests (medium)",
    "eval: LLM evaluation (slow, costs money)",
    "slow: slow tests, skip in CI",
]
addopts = "--strict-markers -m 'not eval and not slow'"

[tool.coverage.report]
fail_under = 70
exclude_lines = [
    "pragma: no cover",
    "raise NotImplementedError",
    "if __name__ == .__main__.:",
]

动作 5:让 CI 跑得快(< 3 分钟目标)

CI 跑得快的三个核心策略:

策略 1 · 并行

4 个 job 并行跑 vs 串行跑,差别非常大:

串行:lint(20s) + typecheck(60s) + architecture(15s) + test(90s) = 3 分 5 秒
并行:max(20s, 60s, 15s, 90s) = 1 分 30 秒

做法:在同一个 workflow 里写多个 job,GitHub Actions 默认并行。

策略 2 · 缓存(cache)

依赖装一次缓存住,下次跑只下载变更的部分:

- name: Install uv
  uses: astral-sh/setup-uv@v3
  with:
    enable-cache: true        # 自动缓存 .venv 和 uv 本身

mypy 也支持缓存:

- name: Cache mypy
  uses: actions/cache@v4
  with:
    path: .mypy_cache
    key: mypy-${{ runner.os }}-${{ hashFiles('**/*.py') }}
    restore-keys: mypy-${{ runner.os }}-

- run: uv run mypy --cache-dir .mypy_cache src/

策略 3 · 选择性跑(path filters)

改文档不应该跑 pytest:

# 单独一个 docs-only 的 workflow
name: Docs
on:
  pull_request:
    paths:
      - 'docs/**'
      - '**.md'
# CI workflow 跳过纯文档改动
on:
  pull_request:
    paths-ignore:
      - 'docs/**'
      - '**.md'

策略 4(进阶) · 测试切分

如果测试本身就 > 5 分钟,分成两个 job 并行跑:

test-unit:
  steps:
    - run: uv run pytest tests/unit -v

test-integration:
  steps:
    - run: uv run pytest tests/integration -v

R·Agent 当前规模下,前三个策略就够了。

动作 6:给 PR 模板加 CI 状态绑定

CI 跑完会在 PR 页面显示 ✅ / ❌。但你还可以在 PR 描述里强制让提交者声明做了什么:

<!-- .github/PULL_REQUEST_TEMPLATE.md -->

## 改了什么

<!-- 一两句话描述变更 -->

## 为什么改

Closes #

## CI Checklist(必填,CI 还会再检查一遍)

- [ ] commit 消息符合 Conventional Commits
- [ ] 通过了 `ruff check` 和 `ruff format --check`
- [ ] 通过了 `mypy`
- [ ] 测试覆盖率 ≥ 70%
- [ ] 没有违反 Hexagonal 边界(`lint-imports` 绿)
- [ ] 如果改了 domain 契约或 BusinessRules,在 PR 描述里明确标注 `BREAKING CHANGE`
- [ ] 如果加了新的 LLM 调用,L2/L3 分离了(没在 LLM 调用函数里加静态方法)

<!-- 怎么测的 -->

<!-- 可能影响哪些模块 -->

6.5 日常操作手册 · 按场景查

🟢 6.5.1 CI 红了怎么办

第一步:别绕过。CI 红意味着规则被违反,要修。

第二步:看错误日志,定位是哪个 job 失败。GitHub Actions 的 UI 会用 ❌ 标记失败的 step。

第三步:根据 job 类型不同,采取不同行动:

失败 Job 含义 行动
lint 代码风格 / lint 规则违反 uv run ruff check --fix . 自动修
typecheck mypy 类型错 加类型注解,或用 # type: ignore[error-code] 局部豁免
architecture Hexagonal 边界违反 见 3.5.6 import-linter 救命指南
test 测试挂了 本地复现 uv run pytest -k <test_name>,定位修复

第四步:本地修完,push,CI 自动重跑。

🟢 6.5.2 CI 慢死了,怎么定位瓶颈

第一步:看每个 step 的耗时。GitHub Actions UI 在每个 step 旁边显示耗时。

第二步:常见瓶颈和对策:

瓶颈 对策
装依赖 30 秒以上 用 uv + cache,降到 5 秒
mypy 跑 2 分钟 加 .mypy_cache 缓存,降到 30 秒
pytest 跑 5 分钟 切分 unit / integration 并行;mock LLM 不跑真实
一个 job 单独慢 看那个 job 的具体 step,继续拆

第三步:如果优化了还慢,接受现实 —— 但要有个明确的”为什么”(比如”我们 LLM 真实调用集成测试每周一晚上跑”)。

🟢 6.5.3 我急着合并,能不能跳过 CI?

两种合法绕过方式(其他都不行):

方式 1 · 紧急修生产 bug(hotfix)

  • 在 PR 标题里加 [HOTFIX]
  • review 一次后允许 admin override
  • 合并后立刻补测试和 fix CI,再开一个 follow-up PR

方式 2 · CI 本身坏了(基础设施故障)

  • GitHub Actions 自己挂了
  • 第三方 action 挂了
  • 这种情况临时禁用某个 job(comment 掉,但留 TODO)

两种不合法的绕过(永远不允许):

  • ❌ git push --force 到 main(branch protection 应该阻止)
  • ❌ 临时关掉 branch protection 然后开回去
  • ❌ --no-verify 跳过 pre-commit hook(本地可以,但 CI 还会拦)

口号:CI 是法律,绕过 CI 是越狱。即使是你自己,也不应该越狱。

🟡 6.5.4 加新规则要不要立即开严格模式?

常见纠结:你想加一条新规则(比如开启 mypy strict = true),但跑一遍发现整个 codebase 有 200 处违反。

怎么处理?

❌ 不要做:直接开严,让所有人的 PR 都挂(团队叛变)

✅ 应该做:渐进式启用

# 阶段 1(本周):只 warn,不 fail
- run: uv run mypy src/ || true
  continue-on-error: true

# 阶段 2(下个月):部分目录严格,其他宽松
[[tool.mypy.overrides]]
module = "src.domain.*"
strict = true
# 其他模块默认宽松

# 阶段 3(三个月内):整个 codebase 严格
[tool.mypy]
strict = true

修复 200 处违反的策略: 1. 新 PR 必须不引入新违反(用 pre-commit 只检查改动的文件) 2. 每周修 20 处历史违反(放进 backlog) 3. 三个月内清零,然后切换到严格模式

🟡 6.5.5 我想加一个新检查,怎么决定值不值

判断标准:加任何 CI 检查前,问自己 3 个问题:

问题 1 · 它能拦住一个真实发生过的 bug 吗?

  • ✅ 能(比如秘钥泄漏检测 → 你或同事曾经 commit 过 .env)
  • ❌ 不能(纯理论 best practice)→ 别加

问题 2 · 它增加多少 CI 时间?

  • < 10 秒 → 大胆加
  • 10-30 秒 → 看价值

  • 30 秒 → 必须有强理由

问题 3 · 误报率高吗?

  • < 5% → OK
  • 5-20% → 配置上让团队习惯,不要直接 fail

  • 20% → 不要加,会引起信任崩溃

例子: - ✅ 加 import-linter 检查 Hexagonal 边界(高价值,低误报) - ✅ 加 detect-secrets(防止真实泄漏) - ⚠️ 加 pylint(误报多,可能让团队烦) - ❌ 加”代码注释覆盖率检查”(浪费时间且伤士气)

🟡 6.5.6 dependabot / renovate 要不要开?

dependabot:GitHub 自带的依赖更新机器人。

开启:在 repo 加 .github/dependabot.yml:

version: 2
updates:
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
  
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "monthly"

好处: - 自动开 PR 升级依赖 - 安全漏洞自动告警

坏处: - PR 多(每周 5-10 个) - 有时升级会 break 你的代码

对你 R·Agent 的建议:开启,但限制到月度,聚焦安全更新。

updates:
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "monthly"
    open-pull-requests-limit: 3
    allow:
      - dependency-type: "direct"
    versioning-strategy: "increase-if-necessary"

🔴 6.5.7 救命:CI 突然全挂了,但代码没改

症状:你昨天 PR 是绿的,今天没改代码,CI 突然全红。

常见原因:

  1. GitHub Actions 服务问题 → 等 30 分钟再试,或看 https://www.githubstatus.com
  2. 第三方 action 升级 break 了 → 检查最近用的 action 版本(锁版本可以避免)
  3. 依赖被删了 / yanked → 看 pip install 的报错
  4. runner 镜像更新了 → 看是不是 Ubuntu 镜像更新

快速诊断:

# 在 GitHub Actions UI 看具体的红色 step,常见关键词:
# - "ResourceNotAccessibleByIntegration" → 权限问题
# - "package X not found" → 依赖问题
# - "image not available" → runner 问题
# - "rate limit exceeded" → 重试或加 token

预防: - 锁所有 action 版本(actions/checkout@v4 而非 @latest) - 依赖装 lockfile(uv sync --frozen) - 关键检查走 dependabot 但不自动 merge

🔴 6.5.8 救命:有人推了一个红色 PR 到 main

症状:不知道怎么的,一个 CI 红的 commit 进了 main。

可能原因:

  1. branch protection 没开 / 配错 → 立刻去 Settings 检查
  2. 有人手动绕过了 → 看 audit log
  3. CI 在那个 commit 时刚好挂了,有人 admin override → 算 hotfix

修复:

# 1. 先恢复 main 到上一个绿色 commit
git checkout main
git revert <bad-commit>
git push origin main

# 2. 修复 branch protection 配置

# 3. 处理那个 commit 引入的问题(可能要补 PR)

长期预防: - 定期 audit branch protection 设置 - 每月看一次 audit log,排查 admin override - 写一个 monitoring script,每天 check main 的最新 commit 是否绿

6.6 行业权威怎么做

Trunk-Based Development 与 CI 的关系

DORA(DevOps Research and Assessment)研究多年得出结论:高绩效团队的 CI 时长 < 10 分钟,部署频率 > 每天一次。

CI 慢直接拖累整个开发节奏。这就是为什么本章把”3 分钟以内”作为目标。

Google 的 Code Review 标准

Google 内部所有代码必须通过 review。但 review 之前,自动检查必须全过:

  • Build green
  • Tests pass
  • Linter clean
  • Type check clean

思路:人的时间贵,机器的时间便宜。机器能查的全交给机器,人只 review 机器查不出来的(设计、可读性、业务正确性)。

Astral(uv / ruff 的公司)的”开发者体验”哲学

Astral 创始人 Charlie Marsh 在 2024 年的演讲里说:

“Python 工具链最大的问题不是功能不够,是太慢、太分散。我们做 ruff 和 uv,核心目标是把开发者的反馈循环压到秒级。”

ruff 比 pylint 快 100 倍,uv 比 pip 快 10-100 倍。这不是炫技,是改变了团队遵守规则的意愿。

Pre-commit 框架的诞生背景

Anthony Sottile(pre-commit 框架作者)在 2014 年提出这个工具,核心论点:

“git pre-commit hook 已经存在 10 年了,但没人用。原因不是技术问题,是配置太麻烦。pre-commit 框架的目标是让团队 30 秒内配好 hook。”

这个观察直接影响了本章的 6.4 动作 1 —— 我推荐你用 pre-commit 框架,不是自己写 shell。

反模式:Jenkins / 自建 CI 的痛苦

不少团队还在用 Jenkins 跑 CI。对小团队是反模式:

  • 要维护 Jenkins server(磁盘、内存、安全更新)
  • pipeline 用 Groovy 写,学习曲线陡
  • 跟 GitHub PR 集成需要插件,经常坏

GitHub Actions 的优势: - 零运维(GitHub 替你跑) - YAML 配置(声明性,易读) - 跟 PR 深度集成(评论、状态、annotation 都自动) - 小项目免费(私有 repo 也给 2000 分钟/月)

Jenkins 适合:大企业、合规要求严、需要自建 runner。R·Agent 完全不适用。

有争议的:要不要追求 100% 自动化

业界有一派声音:“code review 应该 99% 自动,人只看 1%”。

反对方观点:自动化无法检查”设计是否合理”、“命名是否清晰”、“这段代码是否真的解决了问题” —— 这些必须人 review。

本章的立场:自动化做”能验证的规则”,人 review 做”需要判断的设计”。两者分工:

类型 谁查
代码风格 自动(ruff)
类型错误 自动(mypy)
测试通过 自动(pytest)
架构边界 自动(import-linter)
代码可读性 人
命名是否清晰 人
设计是否合理 人
是否真的解决了业务问题 人

机器是机器,人是人,各做各的。

6.8 学会检验 · 你能讲出来吗?

自检 1 · CI 的真正定位是什么?

参考答案:“CI 不是’跑测试的地方’,是门禁(gate)。它把所有想守的规则变成检查项,违反任一规则就拒绝合并。本质是把’违反规则的成本’从 0 变成’PR 无法上线’,让经济激励对齐到遵守规则。”

自检 2 · 为什么要本地 + CI 两道防线?

参考答案:“反馈循环越短,修复成本越低。本地 pre-commit 秒级反馈,但可以被 --no-verify 绕过。CI 慢但强制(branch protection)。两者检查内容应一致,本地是加速,CI 是真相。”

自检 3 · 你的 R·Agent CI 应该跑哪几个 job?

参考答案:“至少 4 个 job 并行:

  1. lint:ruff check + format
  2. typecheck:mypy(domain 严格)
  3. architecture:import-linter 检查 Hexagonal 边界
  4. test:pytest unit + integration,覆盖率 >= 70%

总时长目标 < 3 分钟。慢了团队就开始想绕过。”

自检 4 · 同事说’我急着合并,能不能跳过 CI’,你怎么回应?

参考答案:“问他三个问题:

  1. 是真的紧急生产 bug 吗(hotfix)?还是只是觉得 CI 慢?
  2. 如果跳过,我们怎么保证后续补上(写 follow-up PR)?
  3. 这次跳过的成本(后续 bug、AI 写错也没人拦)你愿意承担吗?

如果不是真的 hotfix,坚持让他过 CI。如果是 hotfix,可以临时 admin override,但要求 24 小时内补 follow-up PR 修复根因。”

自检 5 · 你想加 mypy strict 但发现 200 处违反,怎么处理?

参考答案:“渐进式启用,绝不一刀切:

  1. 阶段 1:用 continue-on-error: true 只 warn 不 fail
  2. 阶段 2:只对 src.domain.* 开 strict,其他模块宽松
  3. 阶段 3:每周修 20 处历史违反,三个月内清零
  4. 阶段 4:整个 codebase 严格

新 PR 必须不引入新违反(可以用 mypy 只检查改动文件),但历史违反慢慢清。这样团队不会叛变,也守住了底线。”

自检 6 · 跟一个架构师聊 R·Agent 的 CI

参考答案(模拟对话):

架构师:“你们 CI 都跑些什么?”

你:“4 个并行 job:lint(ruff)、typecheck(mypy,domain 严格)、architecture(import-linter 检查 Hexagonal 边界)、test(pytest unit + integration,覆盖率 70% 门槛)。总时长大概 2 分钟,跑在 GitHub Actions 上,用 uv 装依赖比 pip 快 10 倍。”

架构师:“CI 红了能强行合并吗?”

你:“不能。Branch protection 开了 ‘Do not allow bypassing the above settings’,管理员也不能直接 push main。只有 hotfix 才允许 admin override,且必须 24 小时内补 follow-up PR。”

架构师:“前面学的所有规范怎么落到 CI 的?”

你:“Conventional Commits → conventional-pre-commit hook。Hexagonal 边界 → import-linter。L2/L3 分离这种语义上的规则机器查不了,靠 code review。测试分层和覆盖率 → pytest-cov + –cov-fail-under。秘钥扫描 → detect-secrets。Commit 消息、代码风格、类型、测试这几条铁律全是 CI 强制。”

架构师:“AI 写代码越来越多,有什么针对的?”

你:“AI 最容易犯的错就是架构边界违反 —— 比如在 domain 里 import claude 库。import-linter 专治这个。还有 AI 会忘记 L3 规则化,但这是语义层面,目前还得靠 code review 拦。”

能这样说话 = 你 R·Agent 的工程治理彻底闭环了。
